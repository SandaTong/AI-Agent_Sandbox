# M7 学习笔记 — DNS 域名维度管控（网络管控从 IP 升到域名）

**面试口径**：M6 我用 WFP 做到了"按进程 / 按 IP 精确管控 outbound"，但 agent 场景真正想表达的是"**只准连 `api.openai.com`，别的域名一律拒**"——问题是 **WFP 内核层根本看不到域名**（域名早在 DNS 解析阶段就变成 IP 了）。所以域名管控必须在 **DNS 解析这一环** 动手。M7 用 **DNS 查询 API Hook**（复用 M4 的注入 + MinHook 骨架）在 target 进程内 hook 域名解析，做域名白名单；并另开一个 demo 演示"域名→IP→WFP"的联动纵深。对应 JD：**网络沙箱 / 域名维度访问控制**。

---

## 一、为什么域名管控是个独立难题：DNS 解析的真实链路

一次 `connect("api.openai.com")` 背后：

```
target 进程
   │  ① 调解析 API：getaddrinfo / GetAddrInfoW / DnsQuery_W
   ▼
Windows DNS Client 服务 (dnscache / svchost)   ← 大部分解析走这里（进程外！）
   │  ② 查缓存，没有则……
   ▼
   ③ 向 DNS 服务器发 UDP/TCP :53 报文（或 DoH 走 :443）
   ▼
   ④ 拿到 IP，返回给 target
   │
   ▼  ⑤ target 用 IP 调 connect() → 进 M6 的 WFP ALE 层
```

**关键事实**：`getaddrinfo` 这类 API 在进程内是个**薄壳**，真正解析通过 RPC 甩给了**进程外的 DNS Client 服务**。这个事实直接决定了三条路线的能力边界。

---

## 二、三条技术路线对比（选型分析）

| | A: DNS API Hook | B: WFP 拦 :53 | C: DNS→IP 联动 |
|---|---|---|---|
| 拦截点 | 进程内解析 API 入口① | 内核 :53 报文③ | hook 拿域名① + WFP 拦 IP⑤ |
| 天然拿到明文域名 | ✅ | 需解析 DNS 报文 | ✅ |
| 能区分是哪个 agent | ✅（进程内） | ❌（源是 svchost 不是 target） | ✅ |
| 挡得住 DoH | ✅（hostname 层） | ❌（DoH 混在 :443） | ✅ |
| 复用已有底子 | M4 直接复用 | M6 但要写 callout driver | M4+M6 都要 |
| 工程量 | 小 | 大（要内核驱动） | 最大 |
| 被 M6"IP 不命中"坑影响 | 否 | 否 | ⚠️ 被卡死 |
| agent 场景贴合 | ⭐⭐⭐ | ⭐ | ⭐⭐（理论好落地难） |

**方案 B 的致命缺陷**：解析走进程外 dnscache，WFP 在 :53 报文上看到的**源进程是 svchost 而非 target**，按 AppID 根本区分不出"是哪个 agent 要解析这个域名"；且 DoH 走 :443 完全绕过 :53 拦截。

**结论**：**A 是唯一在"域名字符串"这个正确抽象层做拦截的方案**，且和 M4 一脉相承（换个 hook 目标而已）。C 作为纵深补充另开 demo。B 需要写内核驱动，放到 M9 再说。

## 三、形态 A：DNS 域名白名单 Hook —— `m7_demo` + `dns_hook.dll`【✅ 完全成功，主力】

### 实现（复用 M4 注入骨架）

```
m7_demo（broker）:
  1. SetEnvironmentVariableW(M7_DNS_ALLOWLIST, "example.com")  ← 白名单经环境变量传
  2. launch target（挂起）
  3. Injector::InjectDll(dns_hook.dll)   ← 远程线程 + LoadLibraryW（M4 同款）
  4. ResumeThread

dns_hook.dll（在 target 进程内）:
  · DllMain attach → 读环境变量 M7_DNS_ALLOWLIST → MinHook 钩 ws2_32!GetAddrInfoW
  · HookedGetAddrInfoW：域名命中白名单 → 调原函数放行
                        未命中 → 返回 WSAHOST_NOT_FOUND（target 拿不到 IP）
```

### 白名单怎么传给注入的 DLL —— 环境变量（零改 core）

`dns_hook.dll` 运行在 target 进程里，需要知道白名单。最干净的做法：broker `SetEnvironmentVariableW(L"M7_DNS_ALLOWLIST", ...)`，`CreateProcessAsUserW(lpEnvironment=nullptr)`（launcher 就是这样）会让子进程**继承 broker 的环境块**，注入的 DLL 在 DllMain 里 `GetEnvironmentVariableW` 读到。不用改 `ProcessLauncher`、不用额外 IPC。

白名单支持三种匹配（`dns_hook.cc` 的 `IsAllowed`）：完全相等 / `*.example.com` 通配 / 裸域 `example.com`（隐式含子域）。

### 实测（target 的 jailbreak-8 两行）

```
[8a] 解析 example.com  (白名单内) : SUCCESS (解析到 104.20.23.154，DNS 未被拦)
[8b] 解析 www.bing.com (白名单外) : BLOCKED (GetAddrInfoW err=11001)  ⭐
```

- `err=11001` = `WSAHOST_NOT_FOUND`（EAI_NONAME）——hook 让白名单外域名"查无此域名"。
- 注入链路日志：`远程线程 LoadLibraryW → DLL 注入成功 → dns_hook.dll 注入成功`。
- DebugView / `%TEMP%\dns_hook_log.txt` 里可见 `[dns] 放行(白名单内)` / `[dns] 拦截(白名单外)`。
- **一次命中**：说明 `GetAddrInfoW` 就是 target（Winsock 标准解析）走的入口，不用再补 hook 其他 API。

### 为什么 hook `ws2_32!GetAddrInfoW`

`getaddrinfo` / Python `socket.getaddrinfo` / Node `dns.lookup` / Go net / curl，在 Windows 上**最终都落到 `ws2_32!GetAddrInfoW`**（宽字符版是底座，窄字符 `getaddrinfo` 内部转调它）。hook 这一个点就能覆盖绝大多数 agent 运行时的域名解析。若遇到直接调 `DnsQuery_W`（dnsapi.dll）的程序，可再加一条 hook 兜住——本 milestone 实测 hello_target 走 `GetAddrInfoW` 即被拦，未额外加。

## 四、形态 C：DNS→IP 联动 M6 WFP —— `m7_ip_demo`【架构演示】

演示"域名→IP→WFP"的联动链路（M4 hook 思路 + M6 WFP 合体）：

```
1. broker 侧自己先解析白名单域名（GetAddrInfoW）→ 拿到"域名 → IP 集合"
   实测：example.com -> 104.20.x.x / 104.20.y.y ...
2. 把这些 IP 交给 WFP 做"只放行白名单域名解析出的 IP"
```

### 为什么要有 C：纵深防御

形态 A 的弱点——**agent 若直接用 IP 连（不解析域名）就绕过了 hook**。C 在 IP 维度补一道：即使绕过域名解析，非白名单 IP 也连不上。**A（hostname 维度）+ C（IP 维度）叠加 = 纵深防御**，正好呼应 agent 场景"既防域名也防裸 IP"。

### ⚠️ C 继承了 M6 的已知本机限制

C 依赖 WFP 按 IP 精确放行/拦截，而 **M6 实测本机纯用户态 `ALE_AUTH_CONNECT_V4` 层 IP 条件不命中**（M6.md § 四）。所以 C 的 IP 联动部分在本机不真正生效——它的价值是**演示 DNS→IP→WFP 的联动架构**。为保证"能拦住 target"这一沙箱语义，`m7_ip_demo` 用 M6 的 **AppID 形态兜底**（按 exe 精确禁 target 全部 outbound），把"域名→IP 解析结果"作为策略信息打印展示。真正落地按 IP 白名单需**内核态 callout**（M9 方向）。

## 五、和 M4/M5/M6 的关系（技术复用图谱）

```
M4 注入 + MinHook（hook CreateFileW，观察文件访问）
   │  换 hook 目标
   ▼
M7-A dns_hook.dll（hook GetAddrInfoW，管控域名）   ← 证明 hook 技术不只能拦文件，也能拦网络
   │  + 
M6 WFP（按 IP/AppID 拦 outbound）
   │  域名→IP 联动
   ▼
M7-C m7_ip_demo（broker 解析域名拿 IP + WFP 兜底）  ← M4 思路 + M6 能力合体
```

- M7-A 是 **M4 的第二个应用**：同一套"注入垫片 + inline hook + trampoline 放行"，hook 点从 `CreateFileW` 换成 `GetAddrInfoW`。
- M7-C 是 **M6 的延伸**：把"IP 从哪来"这个上游（域名解析）接上，形成"域名→IP→内核拦"的完整链路。

## 六、mitigation 冲突提醒（同 M4/M6）

M7-A 要注入 `dns_hook.dll`，所以 target 的 mitigation **必须关掉两位**（`m7_demo.cc` 里已设）：
```cpp
mit_cfg.strict_signed_dll = false;      // 否则拦掉未签名的 dns_hook.dll
mit_cfg.prohibit_dynamic_code = false;  // 否则拦掉 MinHook 改可执行内存
```
这和 M5 是一对镜像——M5 开满这两位来**反注入**，M7-A 关掉它们来**注入自己的管控 hook**。生产做法：hook DLL 签名，或用更早的预置 hook 机制。（所以 jailbreak-3/4 在 M7 下也是 SUCCESS，属预期，见 M5。）

## 七、面试三连问

1. **域名管控为什么不能在 WFP 做？** —— WFP 内核层只看得到 IP，域名在 DNS 解析阶段就没了；且解析走进程外 dnscache，WFP 在 :53 看到的源是 svchost 区分不了进程。要按域名管控必须在进程内 hook 解析 API。
2. **hook 哪个 API、为什么？** —— `ws2_32!GetAddrInfoW`，因为 getaddrinfo/Python/Node/Go/curl 最终都落到它；进程内 hook 能拿明文域名 + 区分进程 + 挡 DoH（DoH 也要先调它拿 hostname）。
3. **域名 hook 的弱点、怎么补？** —— agent 直连 IP（不解析）可绕过；补法是 M7-C 的"域名→IP→WFP"联动，在 IP 维度加第二道关（hostname + IP 纵深）。彻底稳需内核态 callout。
