# M4 学习笔记 — DLL 注入 + API Hook（精简版骨架）

**面试口径**：M0~M3 我一直是"沙箱设计者"，把target 关起来。M4 切换视角——broker 主动往 target 里**注入一个 DLL**，这个 DLL 在 target 内部用 MinHook **Hook 住敏感 API（CreateFileW）**，把 target 的调用重定向到我们的拦截逻辑。**注入 + Hook 在沙箱里不是"攻击"，而是"在target 内部植入一层拦截垫片（interception shim）"** —— 这正是 Chromium sandbox 的做法：target 启动时 broker 注入一层 hook，target 对敏感 API 的调用被无感知地拦截转发。M4 是 M3 IPC 的自然延伸：M3 是 target **主动**请 broker 代劳，M4 是 target 被 hook 后**自动**把敏感调用交出去（target 不用改代码）。

对应 JD：**W4 —— DLL 注入 / API Hook / 反注入**（Richter Ch 22 一整章就是这块）。

---

## 一、M4 的双重视角

```
攻击者视角（技术手段）：              防御者视角（沙箱里的用途）：
broker 往 target 注入 DLL       →   给 target 植入"监控/拦截层"
   ↓                                    ↓
DLL 里 Hook 关键 API             →   target 调 CreateFileW 先过我们的钩子
   ↓                                    ↓
观察/篡改 target 行为             →   钩子里做策略检查 → 可转发给 broker（接 M3 IPC）
```

**M4 精简版只做到"观察"**（钩子打印被访问的路径，然后放行原函数）。把"钩子里做策略检查 + 转发 broker 代劳"留作后续演进——那一步就把 M3 IPC 和 M4 Hook 完全缝起来了。

---

## 二、远程线程注入四件套（core/injector.cc）

目标：让 target 加载 `sandbox_hook.dll`。思路：**借 target 自己的线程去调`LoadLibraryW(L"...\\sandbox_hook.dll")`**。

```
1. VirtualAllocEx(target, path_bytes, PAGE_READWRITE)     在 target 地址空间分配内存
2. WriteProcessMemory(target, remote_mem, dll_path)把 DLL 路径字符串写进去
3. GetProcAddress(kernel32, "LoadLibraryW")               取 LoadLibraryW 地址
   ⭐ kernel32.dll 在同一 session 所有进程加载基址相同，broker 取到的地址在
      target 里同样有效——这是本注入手法成立的前提
4. CreateRemoteThread(target, LoadLibraryW, remote_mem)   在 target 起线程，入口=LoadLibraryW，
      参数=第2步写进的路径地址；等价于 target 自己执行 LoadLibraryW(L"...\\sandbox_hook.dll")
5. WaitForSingleObject + GetExitCodeThread                等远程线程结束；退出码=LoadLibraryW
      返回的 HMODULE 低32 位，非 0 即加载成功
```

**注入成功的硬证据**（实测）：注入后用 `(Get-Process hello_target).Modules` 查 target 的已加载模块列表，能看到：
```
sandbox_hook.dll 路径=D:\...\build_m0\Debug\sandbox_hook.dll
```
—— target 进程里确实多了我们的 DLL。

## 三、MinHook 钩住 CreateFileW（demo/sandbox_hook.cc）

被注入的 DLL 在 `DllMain` 的 `DLL_PROCESS_ATTACH` 里装 hook：

```cpp
MH_Initialize();
MH_CreateHookApi(L"kernel32", "CreateFileW", &HookedCreateFileW, &g_orig_CreateFileW);
MH_EnableHook(MH_ALL_HOOKS);
```

- `HookedCreateFileW`：我们的钩子。target 调 CreateFileW 会先进这里，打印被访问路径，再调 `g_orig_CreateFileW`（MinHook 回填的 trampoline，跳过 hook 直接执行原函数）放行。
- **MinHook 原理**：Inline Hook——改目标函数（CreateFileW）开头几字节为 `jmp 我们的钩子`，同时把被覆盖的原始指令搬到一块 trampoline 里 + 接一个跳回原函数后续的`jmp`。`g_orig_CreateFileW` 就指向这个 trampoline。MinHook 内部用 HDE（Hacker Disassembler Engine）算准指令边界，避免截断半条指令。

**Hook 生效的硬证据**（实测，Medium IL 下文件日志）：
```
[hook] sandbox_hook.dll 已注入并 Hook 住 CreateFileW
[hook] CreateFileW 拦截到: C:\sandbox_share\hook_diag.txt
[hook] CreateFileW 拦截到: CONOUT$
[hook] CreateFileW 拦截到: C:\Users\<你>\Desktop\sandbox_jailbreak.txt   ← ⭐ jailbreak-1!
```
第三行是决定性证据：**jailbreak-1（写用户桌面文件）内部调的 CreateFileW，路径被我们注入的 hook 完整拦到**。

## 四、⭐ M4 亲踩的坑：注入的 hook 垫片"继承 target 权限，不提权"

**现象**：默认（Low IL）跑时，注入成功、hook 也装上了（DebugView 能看到 `[hook]` 日志），但**钩子里写的文件日志 `C:\sandbox_share\hook_log.txt` 死活不出现**。加 `--no-il`（Medium IL）跑，文件日志立刻正常。

**根因**：`C:\sandbox_share` 是普通 Medium IL 目录，**Low IL 的 target 对它没有写权限**（文件系统 mandatory label 拦下，返回 ACCESS_DENIED）。而我们的钩子代码虽然在 target 内存里执行，但它做的文件 IO **仍然以 target 的身份和 IL 进行**——这正是 jailbreak-1 被拦的同一个机制。

**关键教学点**：
> **注入的 hook 垫片继承 target 的权限，不会给 target 提权。** 钩子逻辑（改内存、拦函数）在 target 地址空间里不受 IL 限制；但钩子里发起的任何系统调用（打开文件、连网络）仍受 target 自身沙箱权限（IL / AppContainer / Job / mitigation）约束。想让被hook 的操作"越权"，只能把它**转发给权限更高的 broker 代劳**（这正是 M3 IPC 的意义 + M4 后续要接的方向）。

**日志通道的正确设计**（据此调整）：
- **首选 `OutputDebugStringW`** —— 不受文件系统 IL 限制，DebugView 可实时看，Low/Medium IL 都行
- 文件日志改写到 `%TEMP%`（进程对自己 TEMP 一般有权限），作为 Medium IL 及以上的补充；Low IL 下 `GetTempPathW` 仍指向 Medium 目录写不进，属正常，看 DebugView 即可

## 五、精简版的边界（为什么 M4 不叠加 AppContainer + 强 mitigation）

注入用的 `VirtualAllocEx / WriteProcessMemory / CreateRemoteThread` 需要 broker 对 target 有 `PROCESS_VM_OPERATION / PROCESS_VM_WRITE / PROCESS_CREATE_THREAD` 权限（broker 是父进程 + IL 更高时有）。但：

- **`PROHIBIT_DYNAMIC_CODE` mitigation** 会拦住 hook 改可执行内存（Inline Hook 要VirtualProtect 成可写再改指令）
- **`BLOCK_NON_MICROSOFT_BINARIES`** 会拦住加载我们没签名的 `sandbox_hook.dll`
- **AppContainer** 的Package SID 对 hook dll 所在目录可能没读权限

所以 M4 精简版用**普通 Low IL target**（m4_demo 里主动把 `prohibit_dynamic_code` / `strict_signed_dll` 关掉）演示注入 + hook 骨架。**这本身是个教学点：强 mitigation 和"运行时自己注入 hook"是天然冲突的**——生产做法是 broker 起 target 时就通过更早的机制预置 hook（Chromium 的 interception 在进程启动早期、通过它自己的 loader 完成，不走运行时 CreateRemoteThread），或者给 hook dll 做微软签名。

## 六、代码结构

| 文件 | 角色 | 关键点 |
|---|---|---|
| `core/injector.{h,cc}` | 注入器 | 远程线程四件套；退出码判定加载成败 |
| `demo/sandbox_hook.cc` → `sandbox_hook.dll` | 拦截垫片 | DllMain 装 MinHook；钩子打印路径后放行；日志走 OutputDebugStringW + %TEMP% |
| `demo/m4_demo.cc` | broker | launch(挂起) → InjectDll → ResumeThread → 等退出 |
| `src/third_party/minhook/` | 第三方 | vendored MinHook v1.3.3，主CMake 编成 minhook 静态库 |

**为什么先挂起再注入再 resume**：保证 hook 在 target 执行任何用户代码（包括越狱测试的 CreateFileW）之前就装好，这样 jailbreak-1 能被钩子拦到。`LaunchOptions.start_suspended=true` 让Launch 不自动 resume，由 m4_demo 注入完自己 `ResumeThread`。

## 七、面试话术合集

### 话术 A：注入在沙箱里是"植入拦截垫片"不是攻击

> "M4 我做DLL 注入 + API Hook，但要强调——**在沙箱语境里注入不是攻击手段，是给 target 植入一层拦截垫片**。Chromium sandbox 的 target 进程启动时，broker 就往里注入了一层它叫 interception 的 hook，把 target 对敏感 API 的调用无感知地拦截、转发给 broker 做策略检查。这和我M3 做的 IPC 是一体两面：M3 是 target 主动通过 IPC 请 broker 代劳，M4 是 target 被 hook 后自动把调用交出去——后者对 target 完全透明，不用改一行target 代码，这才是生产级沙箱的做法。"

### 话术 B：远程线程注入四件套 + kernel32 基址一致

> "远程线程注入的核心是借target 自己的线程去调 LoadLibraryW。四步：VirtualAllocEx 在 target 地址空间分配内存，WriteProcessMemory 把 DLL 路径写进去，GetProcAddress 取 LoadLibraryW 地址，CreateRemoteThread 以LoadLibraryW 为入口、路径地址为参数起线程。这里有个关键前提——**kernel32.dll 在同一 session 的所有进程里加载基址相同**，所以 broker 取到的 LoadLibraryW 地址在 target 里直接有效，不用再做地址转换。远程线程的退出码就是 LoadLibraryW 的返回值，非零说明 DLL 加载成功。我用 Process Explorer 或 PowerShell 查 target 的模块列表验证——注入后确实多了 sandbox_hook.dll。"

### 话术 C：Inline Hook 原理（MinHook）

> "我用 MinHook 做 Inline Hook。原理是改目标函数开头几个字节为一条jmp 跳到我的钩子函数，同时把被覆盖的原始指令搬到一块 trampoline 内存，后面接一条jmp 跳回原函数的后续——这样我的钩子执行完调trampoline 就等于调了原函数。难点在'改几个字节'必须落在完整指令边界上，不能截断半条指令，MinHook 内部用 HDE 反汇编引擎算指令长度。相比 IAT Hook（改导入表，只能拦通过导入表调用的），Inline Hook 直接改函数本体，谁调都拦得到，更彻底。"

### 话术 D：注入的 hook 继承 target 权限，不提权（我踩的坑）

> "M4 我踩了一个很有价值的坑：注入成功、hook 也装上了，但钩子里写日志文件死活写不出。查下来是——**target 是 Low IL，钩子里写的那个目录是 Medium IL，Low IL 写不进去**。这让我理解了一个关键点：**注入的 hook 垫片继承 target 的权限，不会给它提权**。钩子改内存、拦函数这些在 target 地址空间里不受 IL 限制，但钩子里发起的系统调用——打开文件、连网络——仍然以 target 的身份和 IL 走完整的访问检查。所以如果想让被 hook 的操作越权，唯一正路是转发给权限更高的 broker 代劳。这也反过来印证了沙箱 IPC 的必要性——**光注入 hook 拦下来还不够，拦下来之后的'代劳'才是broker 的价值**。日志通道我最后改成优先 OutputDebugStringW，因为它不受文件系统 IL 限制。"

### 话术 E：强 mitigation 与运行时注入的冲突

> "M4 精简版我没叠加 AppContainer 和强 mitigation，因为它俩和'运行时自己注入 hook'天然冲突：PROHIBIT_DYNAMIC_CODE 会拦 Inline Hook 改可执行内存，BLOCK_NON_MICROSOFT_BINARIES 会拦加载我没签名的 hook dll，AppContainer 的 Package SID 对 hook dll 目录可能没读权限。这说明一个设计层面的道理——**你自己的沙箱加固手段会拦住你自己的注入**。生产上的解法是把 hook 预置得更早：Chromium 的 interception 是在进程启动早期、通过它自己的 loader 机制完成的，不走运行时 CreateRemoteThread，这样就不和 mitigation 冲突；或者给 hook dll 做微软签名。"

## 七.5、附加知识（消化时的深挖）

消化 M4 时深挖的两个"为什么"，单独沉淀在 [`M4_appendix.md`](M4_appendix.md)：

1. **Inline Hook vs OC Method Swizzling** —— 意图相同（拦截+替换），但 Swizzling 改 runtime 方法表（高层、不改机器码），Inline Hook 直接改函数机器码头字节为 jmp（底层、不依赖运行时）。真正对应 Inline Hook 的是 fishhook / Dobby 而非 Swizzling。
2. **kernel32 共享基址原理** —— 为什么 broker 取的 `LoadLibraryW` 地址能直接喂给 target：kernel32 全系统物理一份（共享只读页），ASLR 对它是"每次开机随机一次、本次开机内所有进程统一基址"，这是安全与性能的刻意折中，也是远程线程注入的地基。

## 八、下一步（M5 预告）

M4 做了"注入 + Hook"，M5 是它的对立面——**反注入 + 运行时检测**：
- `LdrRegisterDllNotification` 监控 DLL 加载（检测别人注入我）
- 检测远程线程（`CreateToolhelp32Snapshot(TH32CS_SNAPTHREAD)`）
- 其实 M1 装的 mitigation（PROHIBIT_DYNAMIC_CODE / BLOCK_NON_MICROSOFT_BINARIES）就是"内核级反注入"——M4 精简版为了能注入把它们关了，M5 会正面讲它们怎么防注入。
