# M1 学习笔记 — Low IL + Mitigation Policy + Alternate Desktop

**面试口径**：在 M0 的 Job + Restricted Token 之上，M1 加了**三层护栏**——把 target 的 Integrity Level 降到 Low，通过 STARTUPINFOEX 装了 8 项 Process Mitigation Policy（禁子进程/ 禁动态代码 / 只允许微软签名 DLL / 强ASLR ...），再用独立 WindowStation+Desktop 做 UI 隔离。这套组合下来 target **几乎无法作恶**，即使 target 里跑一段任意代码也很难跳出沙箱。

---

## 一、这次学到的三块核心知识

### 1. Integrity Level（IL / Mandatory Label）

**它是什么**：
Access Token 里除了 UserSid / Groups / Privileges 外，还有一个**Mandatory Label** 字段（结构体 `TOKEN_MANDATORY_LABEL`），本质是一个 SID：`S-1-16-<RID>`。RID 决定完整性等级：

| Level     | RID (hex) | 用途 |
|---|---|---|
| Untrusted | 0x0000    | 最低，AppContainer / IE Protected Mode 用|
| Low     | 0x1000    | 沙箱典型选择（我们 M1 就用这个） |
| Medium    | 0x2000    | 普通用户进程 |
| High      | 0x3000    | 管理员进程（UAC 提权后） |
| System    | 0x4000    | SYSTEM 账户 |

**它怎么起作用**：
系统对内核对象（文件、注册表、命名管道、Job、共享内存……）做访问检查时：

1. 先看客体的 **Mandatory Label ACE**——如果客体标了 "Medium 及以上可写"，Low IL 主体**直接被拒**，根本不看 DACL
2. 再走 DACL（我们熟悉的 owner/group/deny/allow ACE）

**NTFS 默认 ACL 的秘密**：普通用户目录（比如 `%USERPROFILE%\Desktop`）没有显式的 Mandatory Label ACE，但系统内建"IL 优先"策略——**Low IL 进程默认无法写任何 Medium 或以上标签的对象**。所以 target 一降到 Low：
- `CreateFileW(桌面\1.txt, WRITE)` → `ERROR_ACCESS_DENIED`
- `RegSetValueEx(HKCU,...)` → 大概率 ACCESS_DENIED（HKCU 有 IL 屏障）
- 只能读写 **`%USERPROFILE%\AppData\LocalLow`** 和 **`%TEMP%\Low`** 等专门开放给 Low 的位置

**我们的代码**：
```cpp
// token_manager.cc
wchar_t sid_str[32];
swprintf_s(sid_str, L"S-1-16-%u", static_cast<unsigned>(level));  // "S-1-16-4096"
ConvertStringSidToSidW(sid_str, &label_sid);

TOKEN_MANDATORY_LABEL tml{};
tml.Label.Sid = label_sid;
tml.Label.Attributes = SE_GROUP_INTEGRITY;

SetTokenInformation(token, TokenIntegrityLevel, &tml,
                    sizeof(TOKEN_MANDATORY_LABEL) + GetLengthSid(label_sid));
```

关键坑：`SetTokenInformation` 传的**大小要包含 SID 本身的字节数**，不是 `sizeof(TOKEN_MANDATORY_LABEL)`。

### 2. Process Mitigation Policy（进程缓解策略）

**它是什么**：
Windows 7 起微软陆续加的一堆"从进程一诞生就绑定的强化开关"。启用后**内核加载器 / syscall 分发器 / 内存分配器直接按策略工作，target 无法在运行时关闭**。

**M1 装的 8 项**：

| 策略 | 常量 | 效果 |
|---|---|---|
| DEP | `..._DEP_ENABLE` | Data Execution Prevention，栈/堆不可执行 |
| Bottom-up ASLR | `..._BOTTOM_UP_ASLR_ALWAYS_ON` | 堆栈基址随机 |
| Force Relocate | `..._FORCE_RELOCATE_IMAGES_ALWAYS_ON` |拦掉"没启用 ASLR 的 DLL"—— 老 DLL 无法加载 |
| **只允许微软签名 DLL** | `..._BLOCK_NON_MICROSOFT_BINARIES_ALWAYS_ON` | **反注入绝杀**：任何非微软签名的 DLL 都无法加载进这个进程 |
| **禁动态代码** | `..._PROHIBIT_DYNAMIC_CODE_ALWAYS_ON` | `VirtualAlloc(PAGE_EXECUTE_READWRITE)` 失败，JIT/shellcode 无门 |
| **禁 Extension Points** | `..._EXTENSION_POINT_DISABLE_ALWAYS_ON` | 拦 AppInit_DLLs、SetWindowsHookEx 全局钩子、IME 注入 |
| 禁远程映像 | `..._IMAGE_LOAD_NO_REMOTE_ALWAYS_ON` | 从 UNC 路径（`\\server\share`）加载 DLL 失败 |
| 禁低完整性映像 | `..._IMAGE_LOAD_NO_LOW_LABEL_ALWAYS_ON` | 加载低 IL 目录里的 DLL 失败 |

**外加一个独立槽位**（不在 Mitigation Policy 位图里）：
- `PROCESS_CREATION_CHILD_PROCESS_RESTRICTED`——**禁子进程**。target 调`CreateProcess` 直接返回 ACCESS_DENIED。**沙箱标配**。

**它怎么装**（架构关键）：

Windows Vista 起`CreateProcess` 有一个扩展入口叫 `STARTUPINFOEX`：

```cpp
STARTUPINFOEXW six{};
six.StartupInfo.cb = sizeof(STARTUPINFOEXW);
six.lpAttributeList = /* PROC_THREAD_ATTRIBUTE_LIST 指针 */;

CreateProcessAsUserW(..., EXTENDED_STARTUPINFO_PRESENT, ...,
                    reinterpret_cast<LPSTARTUPINFOW>(&six), ...);
```

`PROC_THREAD_ATTRIBUTE_LIST` 是一段变长内存，用三个 API 操作：

```cpp
SIZE_T needed;
InitializeProcThreadAttributeList(nullptr, N, 0, &needed);  // 问大小
buffer.resize(needed);
InitializeProcThreadAttributeList(buffer.data(), N, 0, &needed);  // 建列表

UpdateProcThreadAttribute(list, 0,
    PROC_THREAD_ATTRIBUTE_MITIGATION_POLICY,
    &policy_bits, sizeof(policy_bits),  // 位图
    nullptr, nullptr);

UpdateProcThreadAttribute(list, 0,
    PROC_THREAD_ATTRIBUTE_CHILD_PROCESS_POLICY,
    &child_policy, sizeof(DWORD),
    nullptr, nullptr);

// ... 用完清理 ...
DeleteProcThreadAttributeList(list);
```

**我们把这套逻辑封装在了 `MitigationAttrList` 类里**，构造→Configure→用ptr()→析构自动清理。

**为什么它比 Job/Token更强**：
Job/Token 是"事后拦截"——API 调用时判断 → 早期漏洞可能绕过。
Mitigation Policy 是"胎里带"——从进程建EPROCESS 那一刻内核就知道这些策略，加载器/syscall 分发器/内存分配器**没得选**，绕不过（除非能绕内核）。

### 3. Alternate Winstation + Desktop（UI 侧隔离）

**Windows GUI 三层命名空间**（读书对应：MS Docs "Window Stations"）：

```
Session（登录会话，包含用户所有 GUI 状态）
  └── WindowStation（"WinSta0" 是可交互的，其他都不可见）
    └── Desktop（"Default"、"Winlogon"、"ScreenSaver"...）
   └── HWND（窗口，属于 desktop）
```

**M0 的漏洞**：即使削了privilege、加了 Job UI 限制，target 还住在你的 `WinSta0\Default` 上——`EnumWindows` 出来能看到你所有的窗口。虽然 `SendMessage` 会被 UIPI 拦一部分，但**这是"和你共享桌面"的语义**，很多测试仍然可以。

**M1 修复**：
```cpp
HWINSTA new_winsta = CreateWindowStationW(L"sandbox_winsta_xxxx", 0,
                                          WINSTA_ALL_ACCESS, nullptr);
SetProcessWindowStation(new_winsta);  // broker 临时切进去
HDESK new_desktop = CreateDesktopW(L"sandbox_desk", nullptr, nullptr, 0,
                                 kDesktopAllAccess, nullptr);
SetProcessWindowStation(saved_winsta);// broker 立刻切回来

// target 启动时：
STARTUPINFOEX six{};
six.StartupInfo.lpDesktop = L"sandbox_winsta_xxxx\\sandbox_desk";  // 目标桌面
// CreateProcess... 里 target 会自动 attach 到这个 winsta+desktop
```

**broker 为什么要"临时切进新winsta"**：
`CreateDesktop` 只能**在当前线程的 winsta 里创建 desktop**——不允许跨 winsta 建。所以流程必须是：
1. `SetProcessWindowStation(new_winsta)` 临时切
2. `CreateDesktop` 在新 winsta 里建
3. `SetProcessWindowStation(saved_winsta)` 立刻切回来（否则 broker 自己都看不到桌面对话框）

**broker 必须保持 winsta+desktop handle 存活**：
一旦 broker 关闭这两个 handle 且没有其他进程引用，系统会**销毁 winsta**，target 立刻挂掉。所以 `DesktopIsolation` 必须活到 target 退出之后。

**Job UI 限制 vs Alt Desktop 的分工**：
- Job UI 限制（M0）= "拦 target 通过 USER API 操作系统对象"（改剪贴板、切桌面、锁工作站）
- Alt Desktop（M1）= "让 target 通过窗口消息看不到别的进程窗口"（EnumWindows / FindWindow / SendMessage）
两层**互补，不替代**。

## 二、启动流水线的升级

**M0 版本**：
```
CreateRestrictedToken
   ↓
CreateProcessAsUserW (CREATE_SUSPENDED, STARTUPINFOW)
   ↓
AssignProcessToJobObject
   ↓
ResumeThread
```

**M1 版本**：
```
CreateRestrictedToken
   ↓
SetTokenInformation(TokenIntegrityLevel, Low)      ← 新增
   ↓
MitigationAttrList.Configure(...)     ← 新增
   ↓
DesktopIsolation.Create()           ← 新增
   ↓
CreateProcessAsUserW (CREATE_SUSPENDED
    + EXTENDED_STARTUPINFO_PRESENT       ← 关键 flag
    + STARTUPINFOEX::lpAttributeList  = mitigation list
    + STARTUPINFOEX::StartupInfo.lpDesktop = "sandbox_winsta\\sandbox_desk")
   ↓
AssignProcessToJobObject
   ↓
ResumeThread
```

Job 的 assign 依然在 resume 之前——CREATE_SUSPENDED 三步舞的核心不变。

## 三、面试话术模板

> "我在 M1 里给沙箱加了三层：
>
> 第一层是 **Access Token 完整性降级**——用 `SetTokenInformation(TokenIntegrityLevel)` 把 target 的 Mandatory Label SID 改成 `S-1-16-4096`（Low）。降完之后 target 尝试写你桌面上的任何文件都会返回 `ERROR_ACCESS_DENIED`——NTFS 的默认 mandatory ACE 会一票否决。
>
> 第二层是 **Process Mitigation Policy**。我用 `STARTUPINFOEX` + `UpdateProcThreadAttribute(PROC_THREAD_ATTRIBUTE_MITIGATION_POLICY)` 一次装了 8 项：DEP、强ASLR、只允许微软签名 DLL 加载（这是反注入的绝杀，`BLOCK_NON_MICROSOFT_BINARIES`）、禁动态代码（`PROHIBIT_DYNAMIC_CODE`）、禁 Extension Points（拦 AppInit_DLLs 和全局 hook）、禁远程映像、禁低完整性映像。另外用独立的 `PROC_THREAD_ATTRIBUTE_CHILD_PROCESS_POLICY` 属性禁掉了 target 起子进程的能力。这层的关键价值是它是 target 一诞生就绑到EPROCESS 上的，运行时无法关闭，比 Job/Token 的事后拦截更强。
>
> 第三层是 **UI 隔离**——用 `CreateWindowStation` + `CreateDesktop` 建了一对独立的隔离桌面，通过 `STARTUPINFO::lpDesktop` 把 target 塞进去。Target 的 `EnumWindows` 出来的窗口列表基本是空的，Send/PostMessage 也发不到用户桌面上的进程。
>
> 这三层加上 M0 的 Job + Restricted Token 一共五层，覆盖了 JD 里W1 进程管控除了 AppContainer 之外的全部要点。AppContainer 我M2 会做。"

## 五、下一步（M2 预告）

M1 已经把"权限收敛"做到用户态能做的**极限**了。M2 会做**现代Windows 沙箱的顶配**：

- **AppContainer**：用 `CreateAppContainerProfile` 建一个 AppContainer profile，用 **NtCreateLowBoxToken**（未文档化的 native API，但 Chromium sandbox 也用）派生 LowBox Token
- **Capability SIDs**：AppContainer 用白名单式 Capability 机制——target 想访问网络 → 你显式给它 `internetClient` capability；想访问文件系统 → 显式给（大部分不给）
- **AppContainer 独立对象命名空间**：AppContainer 的 mutex、事件、命名管道自动位于 `\Sessions\<n>\AppContainerNamedObjects\<sid>\` 下，天然和别的进程隔离

M2 完成后 target 就变成一个"跟 IE Protected Mode / Edge renderer 同等级别"的沙箱进程。

## 七、踩坑记录：4 次 `0xC0000142` 深度追杀（M1 精华）

M1 让 target 稳定起来花的时间远比预期长——一路踩了 **4 个坑**，每一个都让 target 抛 `STATUS_DLL_INIT_FAILED (0xC0000142)`。这一节完整记录 4 个坑的**发现路径 / 根因 / 修法**，全部是 Windows 沙箱工程师的必修课。

### 越狱测试的最终成绩单（M1 收官）

```
[+] TokenManager: Integrity Level 已降至 Low
[+] MitigationAttrList: 已装配 policy=0x110101100010103 child_process_disabled=1
[+] DesktopIsolation: 隔离桌面已就绪 -> sandbox_winsta_xxxxxxxx\sandbox_desk
[target] integrity_level=Low
[jailbreak-1] 写用户桌面文件 : BLOCKED (gle=5)     ← Low IL / NTFS mandatory ACE
[jailbreak-2] 起子进程 cmd.exe : BLOCKED (gle=367)  ← CHILD_PROCESS_RESTRICTED
[jailbreak-3] 分配 RWX 内存    : BLOCKED (gle=1655) ← PROHIBIT_DYNAMIC_CODE
[jailbreak-4] 加载非签名 DLL   : BLOCKED (gle=577)  ← BLOCK_NON_MICROSOFT_BINARIES
[jailbreak-5] 读剪贴板         : BLOCKED (gle=5)  ← Job UI Limit READCLIPBOARD
```

**5/5 全拦下**。特别是 **gle=577 (ERROR_INVALID_IMAGE_HASH)** —— 内核在做微软签名的 Authenticode 校验时把 DLL 拒了，这是 mitigation policy 生效的**内核层证据**。

### 坑 #1：`BLOCK_NON_MICROSOFT_BINARIES` 拦掉 Debug CRT

**表现**：target 弹"应用程序无法正常启动 (0xc0000142)"，broker 显示 `Target 退出，exit_code=0xc0000142`。

**排障**：
1. broker 日志显示 mitigation policy = `0x110101100010103` 含 `BLOCK_NON_MICROSOFT_BINARIES`
2. `dumpbin /dependents hello_target.exe` 发现 target 依赖 `VCRUNTIME140D.dll`、`ucrtbased.dll`、`MSVCP140D.dll`
3. 这些 Debug CRT DLL **是微软发布的**，但**不带 Microsoft 根证书链的 code signing**——只有 Store 上架的 Release UCRT 才有

**根因**：`BLOCK_NON_MICROSOFT_BINARIES` 不是"拦不是微软出品的 DLL"，而是"内核用微软根证书白名单对每个映像做 Authenticode 校验，凡是校验不过的一律不允许映射进本进程地址空间"。Debug CRT 都过不了这个校验。

**修法**：CMake 里给 `hello_target` 和 `unsigned_probe` 设 `MSVC_RUNTIME_LIBRARY = MultiThreaded$<$<CONFIG:Debug>:Debug>`——**静态链接 CRT**（`/MTd`）。所有 CRT 代码打进 target 自身的 `.text` 段，加载器不再拉外部 DLL，mitigation 通过。

生产环境三种正确选择：静态链接 CRT / 用 Release + Store UCRT / 用 `_AUDIT` 变体先跑一次（mitigation 只写事件日志不真拦——**Chromium sandbox 部署 mitigation 的标准姿势**）。

### 坑 #2：`SetSecurityInfo` 遭遇 `ACCESS_DENIED`

**表现**：修完坑 #1 后 broker 显示 `DesktopIsolation.Grant 失败: [5] Access is denied.`

**排障**：怀疑 Alt Desktop 默认 DACL 挡了 Low IL target，用 `SetSecurityInfo` 事后加 Everyone ACE。结果 `SetSecurityInfo` 自己返回 `ACCESS_DENIED (gle=5)`。

**根因**：`GetSecurityInfo` / `SetSecurityInfo` 内部要求句柄具备 **`WRITE_DAC`** 权限。而 `CreateWindowStation(WINSTA_ALL_ACCESS, ...)` 传入的 `WINSTA_ALL_ACCESS` **并不包含 `WRITE_DAC`**——它只是 `WINSTA_ENUMDESKTOPS / READATTRIBUTES / ACCESSCLIPBOARD / CREATEDESKTOP` 等细分权限位的聚合，不含 STANDARD_RIGHTS 家族的元操作位。

**修法**：**在 Create 时就通过 `SECURITY_ATTRIBUTES` 传入完整 SD，不做事后修改**。SDDL `D:(A;;GA;;;WD)(A;;GA;;;BA)(A;;GA;;;SY)` → `ConvertStringSecurityDescriptorToSecurityDescriptorW` → 填给 `CreateWindowStation` 的 lpSA。**能在创建时传入正确 SD 就永远不要事后 SetSecurityInfo** —— Chromium sandbox 的 `alternate_desktop.cc` 就是这么做的。

### 坑 #3：Job UI 限制和 Alt Desktop 冲突

**表现**：修完坑 #2 target 还挂。此时已排除 mitigation 和 DACL 两个方向。

**排障**：写了一个 `--strict N [--no-desk]` bisect 工具跑 18 种组合：

| 配置 | 结果 |
|---|---|
| `--strict 0 --no-desk` | ✅ 起 |
| `--strict 0` (desk on)       | ❌ 挂 |
| `--strict 8 --no-desk`   | ✅ 起 |

**唯一变量是 desk 开关**——元凶就是 Alt Desktop。

**根因（时序图）**：
```
1. CreateProcess (CREATE_SUSPENDED)
2. AssignProcessToJobObject       ← Job UI 限制此时生效
3. ResumeThread
4. ntdll 加载 user32.dll
5. user32 DllMain → NtUserProcessConnect
6. NtUserProcessConnect 要 attach 到 STARTUPINFO::lpDesktop 指定的 desktop
7. attach 走 NtUserOpenDesktop → 被 JOB_OBJECT_UILIMIT_DESKTOP + UILIMIT_HANDLES 拦下
8. user32 DllMain 返回 FALSE → STATUS_DLL_INIT_FAILED (0xC0000142)
```

**修法**：**Job UI 限制和 Alt Desktop 是互斥的两种 UI 隔离手段**。用 Alt Desktop 做 UI 隔离时，把 Job 的 `UILIMIT_DESKTOP` 和 `UILIMIT_HANDLES` 位清掉。两层分工：

- Job UI 限制 = 在**共享桌面**场景拦 target 的破坏操作（M0 场景）
- Alt Desktop = 在**独立桌面**场景让 target 看不到别的窗口（M1 场景）

Chromium sandbox 走 Alt Desktop 路线；Google Sandbox2（Linux）走 UI 限制路线。**别俩都开**。

### 坑 #4：Mandatory Label 阻断 Low IL 进入 Desktop（最深一层）

**表现**：修完坑 #3 target 仍挂。mitigation / DACL / Job UI 冲突全部排除。

**排障**：意识到 Windows 访问检查**根本不是单层 ACL**：
```
访问检查 = DACL 允许 AND Mandatory Label 允许
```

DACL 我已经开到 Everyone 了。那问题一定在 **Mandatory Label** 层。用 Get-Acl / WinObj 查看隔离 winsta 的 SD，发现它从父 winsta（`WinSta0`）继承了一条 label ACE，等级是 **System 或 High IL**。Low IL target `NoWriteUp` 到 System label 一票否决。

**根因**：Windows 内核安全模型是**双门**：
1. **DACL**：按 SID 匹配（Everyone / User / Group）
2. **Mandatory Label**（住在 SACL 里）：按 IL 数字比较

**两层都过才放行**。SDDL 里 `D:` 段管 DACL，`S:` 段既可以放传统 SACL（审计 ACE），也可以放 mandatory label ACE。

**修法**：SDDL 里加 `S:(ML;;;;;LW)`——把 desktop 的 mandatory label 降到 Low (`LW` = Low Mandatory Level = `S-1-16-4096`)。Low IL target 就能通过完整性检查。

最终生效的 SDDL：
```
D:(A;;GA;;;WD)(A;;GA;;;BA)(A;;GA;;;SY)
S:(ML;;;;;LW)
```

### 四条金牌面试话术（背下来面试直接用）

#### 话术 A：`BLOCK_NON_MICROSOFT_BINARIES` 的真实语义

> "M1 里我调 0xC0000142 花了大量时间。第一层是 `BLOCK_NON_MICROSOFT_BINARIES` 拦掉了 Debug CRT。踩过这个坑我才理解这个 mitigation 的真实语义——**它不是 '拦不是微软出品的 DLL'，而是 '内核用微软根证书白名单对每个映像做 Authenticode 校验'**。Debug 版 CRT DLL 是微软发布的但不带微软根签名（只有 Store 上架的 Release UCRT 才有），所以照样被拒。修法是让 target 静态链接 CRT。生产上还有个 audit 模式的做法——把 `ALWAYS_ON` 换成 `AUDIT`，mitigation 只写日志不真拦，先跑一遍看哪些 DLL 会被误伤，再决定放行策略。这是 Chromium sandbox 部署 mitigation 的标准姿势。"

#### 话术 B：kernel object access rights 不是整体 bitmap

> "第二层坑是 `SetSecurityInfo` 遭遇 `ACCESS_DENIED`。原因是 `CreateWindowStation` 时传入的 `WINSTA_ALL_ACCESS` 只是 winsta 层的细分位聚合（`ENUMDESKTOPS / READATTRIBUTES / ACCESSCLIPBOARD / CREATEDESKTOP` 等），**不包含 `WRITE_DAC`**。而 `SetSecurityInfo` 改 DACL 必须要 `WRITE_DAC` 权限。这教会我一件事：**Windows kernel object 的 access rights 不是整体 bitmap，每一个 API 都期望具体的权限位**。`XXX_ALL_ACCESS` 常量往往不包含元操作位（`WRITE_DAC` / `WRITE_OWNER` / `READ_CONTROL`），这些属于 `STANDARD_RIGHTS` 家族。第二版我改用 SDDL 字符串在 Create 时通过 `SECURITY_ATTRIBUTES` 一次到位——**能在对象创建时传入正确 SD 的场景，永远不要事后 SetSecurityInfo**。"

#### 话术 C：Job UI 限制 vs Alt Desktop 冲突（时序推理）

> "第三层坑是 Job UI 限制和 Alt Desktop 冲突。我用 `--strict N [--no-desk]` bisect 工具跑了 18 种组合定位到 desk 开关就是元凶。根因涉及一段隐藏时序：target 起来后 `user32.dll` DllMain 里的 `NtUserProcessConnect` 要 attach 到 `STARTUPINFO::lpDesktop` 指定的 desktop，这个 attach 内部调 `NtUserOpenDesktop`——恰好被 Job 的 `UILIMIT_DESKTOP` + `UILIMIT_HANDLES` 拦下，user32 DllMain 返回失败，报 `STATUS_DLL_INIT_FAILED`。**Job UI 限制和 Alt Desktop 是互斥的两种 UI 隔离手段，选一个即可**。Chromium sandbox 走 Alt Desktop，Google Sandbox2 走 Job UI 限制。"

#### 话术 D：Windows 访问检查是双门（DACL + Mandatory Label）

> "第四层坑最深也最值钱。DACL 我已经加了 Everyone 全权限，target 还是进不去 desktop。最后意识到 **Windows 访问检查不是单层 ACL，而是 DACL 和 Mandatory Label 的与门**——DACL 按 SID 匹配，Mandatory Label 按 IL 数字比较，两层都过才放行。desktop 从父 winsta 继承了一个 System IL 或 High IL 的 label，Low IL target `NoWriteUp` 到 System label 被拒。修法是在 SDDL 里加 `S:(ML;;;;;LW)`，把 desktop 完整性层的门槛降到 Low。**这个坑教我理解了 Windows 内核安全模型的完整轮廓**——Chromium sandbox 的 `alternate_desktop.cc` 里就是这么做的。Alex Ionescu 有一篇博客详细讲这个双门结构。"

### 这四条踩坑经历的组合价值

面试里能连贯讲出这 4 层（**mitigation policy 语义 → kernel object access rights 结构 → UI 隔离两种手段互斥 → Windows 访问检查双门**），是 **Windows 沙箱工程师的完整技术画像**。四条串起来面试官会明显感觉到"这人真做过、真调过、真读过 Chromium sandbox"，不是背 API。

## 八、越狱测试三档对比表（M1 实测证据链）

**这张表是 M1 最重的一份"证据链"，面试直接放出来**。5 项测试 × 3 档配置：

| # | 越狱动作 | baseline<br>（无沙箱） | M0<br>（Job + Restricted Token） | M1<br>（+ Low IL + Mitigation + AltDesk） | M1 拦截的具体机制 |
|---|---|---|---|---|---|
| 1 | 写 `%USERPROFILE%\Desktop\poc.txt` | ✅ SUCCESS | ✅ SUCCESS | ❌ **BLOCKED gle=5** | Low IL / NTFS mandatoryACE |
| 2 | `CreateProcess("cmd.exe")` 起子进程 | ✅ SUCCESS | ✅ SUCCESS | ❌ **BLOCKED gle=367** | `PROC_THREAD_ATTRIBUTE_CHILD_PROCESS_POLICY` |
| 3 | `VirtualAlloc(PAGE_EXECUTE_READWRITE)` | ✅ SUCCESS | ✅ SUCCESS | ❌ **BLOCKED gle=1655** | `PROHIBIT_DYNAMIC_CODE` |
| 4 | `LoadLibrary(unsigned_probe.dll)` | ✅ SUCCESS | ✅ SUCCESS | ❌ **BLOCKED gle=577** ⭐ | `BLOCK_NON_MICROSOFT_BINARIES` |
| 5 | `GetClipboardData(CF_UNICODETEXT)` | ✅ SUCCESS | ✅ SUCCESS | ❌ **BLOCKED gle=5** | Job `UILIMIT_READCLIPBOARD` |

**关键观察**：
1. **M0 拦下 0 / 5**——只有 privilege 层收敛在这 5 个越狱场景下**几乎无用**，凸显 M1 的必要性
2. **M1 拦下 5 / 5**——每一层都有明确的内核层错误码作为证据
3. **gle=577 (ERROR_INVALID_IMAGE_HASH)** 特别值得注意——**内核在计算映像 Authenticode 哈希、比对微软根证书那一步就把它拒了**。这是 mitigation policy 生效的**内核层证据**，不是 API 装装样子

### 面试话术（放出对比表时用）

> "M1 效果我用一张越狱对比表说明。左边基线组5/5 全穿，M0 5/5 也全穿——只有 Job + Restricted Token 层几乎无用；M1 上了 Low IL + Mitigation Policy + Alt Desktop 之后 5/5 全拦。每一项都有对应的内核层错误码：写桌面 gle=5 (ACCESS_DENIED，Low IL mandatory ACE 拦下)；起子进程 gle=367 (CHILD_PROCESS_POLICY 拦下)；申请 RWX 内存 gle=1655 (PROHIBIT_DYNAMIC_CODE 拦下)；**加载非签名 DLL gle=577 (INVALID_IMAGE_HASH，`BLOCK_NON_MICROSOFT_BINARIES` 在内核映像哈希校验那一步拒的)**；读剪贴板 gle=5 (Job UI Limit 拦下)。**gle=577 是 mitigation policy 生效最硬核的证据**——不是 API 层拦，是内核加载器的验签路径拦。"
