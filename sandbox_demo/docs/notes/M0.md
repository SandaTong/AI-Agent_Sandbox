# M0 学习笔记 — Job / Token / 启动流水线 基础闭环

**面试口径**：我把 sandbox demo 拆成 `common / core / demo` 三层，`core` 里 `JobManager` + `TokenManager` + `ProcessLauncher` 三块可组合，`ProcessLauncher` 按 **CREATE_SUSPENDED → AssignProcessToJobObject → ResumeThread** 的顺序保证限制在目标进程执行第一行指令之前就已经生效。

---

## 1. 修的3 个硬伤

### 硬伤 1：`JOB_OBJECT_LIMIT_BREAKAWAY_OK` 语义写反

**原代码**：
```cpp
limits.BasicLimitInformation.LimitFlags =
    JOB_OBJECT_LIMIT_BREAKAWAY_OK | ...;
```

**问题**：这个 flag 的语义是 **"允许子进程使用 `CREATE_BREAKAWAY_FROM_JOB` 脱离 Job"**——这是给普通 job（比如批处理调度）用的，让某些子进程可以离开父job。**沙箱场景要的正好是反过来**：一个进程进了 job 就永远在里面，任何 fork 出来的子进程也**自动进入 job**，谁也别想跑。

**M0 修正**：完全不设`BREAKAWAY_OK`，改成设：
- `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` — Broker 的最后一个 handle 一关，job 里所有进程立刻被内核终结，防止孤儿。
- `JOB_OBJECT_LIMIT_DIE_ON_UNHANDLED_EXCEPTION` — target崩了不弹 WER对话框。

**观测证据**（demo 输出）：notepad 在 Win11 会拉一个子进程，我们没开 breakaway，两个进程都进了job ——`Active processes in job: 2`。

---

### 硬伤 2：两次 `SetInformationJobObject(ExtendedLimit)` 相互覆盖

**原代码**：
```cpp
JOBOBJECT_EXTENDED_LIMIT_INFORMATION limits{};     // struct A
limits.BasicLimitInformation.LimitFlags = ACTIVE_PROCESS | ...;
limits.BasicLimitInformation.ActiveProcessLimit = 5;
SetInformationJobObject(job, ExtendedLimit, &limits, ...);

// ... 后面 ...

JOBOBJECT_EXTENDED_LIMIT_INFORMATION mem_limits{};  // struct B（全新零值）
mem_limits.ProcessMemoryLimit = 200 * 1024 * 1024;
mem_limits.BasicLimitInformation.LimitFlags |= JOB_OBJECT_LIMIT_PROCESS_MEMORY;
SetInformationJobObject(job, ExtendedLimit, &mem_limits, ...);
```

**问题**：`JobObjectExtendedLimitInformation` 这个 info-class 是**整块覆盖**语义。第二次调用送进去的 `mem_limits` 是全新零值的结构体，只填了 `ProcessMemoryLimit` 和 一个 flag，**其他字段全是 0**——所以第一次设的 `ActiveProcessLimit=5` 和 `KILL_ON_JOB_CLOSE / DIE_ON_UNHANDLED_EXCEPTION` 全被清零。

**编译能过**（结构体合法）→ **运行不crash**（API 成功返回）→ **功能悄悄失效**。这类隐蔽bug 是 code review 的高分题。

**M0 修正**：合并成**一次调用**，一个 `JOBOBJECT_EXTENDED_LIMIT_INFORMATION` 里同时填`LimitFlags`、`ActiveProcessLimit`、`ProcessMemoryLimit`。CPU 限速和 UI 限制走的是**不同的 info-class**（`JobObjectCpuRateControlInformation` / `JobObjectBasicUIRestrictions`），互相不覆盖，可以分开调。

---

### 硬伤 3：`AssignProcessToJobObject` 时机错——先启动后加限制

**原代码**：
```cpp
CreateProcessAsUserW(..., 0, ...);        // 用了 0 flags，进程立即开始执行
AssignProcessToJobObject(job, hProcess);  // 后 assign
```

**问题**：从 `CreateProcess` 返回到 `AssignProcessToJobObject` 调用完成，**中间有一个不确定长度的窗口**，target 已经在执行代码了。这段时间里：
- Job 的 memory limit 没生效 → target 可以 `VirtualAlloc` 大内存；
- CPU cap 没生效 → target 可以起 100 个线程死循环；
- UI 限制没生效 → target 可以先把剪贴板改了再 assign；
- Win7 时代甚至可能 assign 失败。

**M0 修正**：走标准三步舞：

```cpp
CreateProcessAsUserW(..., CREATE_SUSPENDED, ...);   // target 主线程冻结
AssignProcessToJobObject(job, hProcess);            // 装Job
// M1 会在此插入：设 IL、装Mitigation
ResumeThread(hMainThread);                          // target 第一行代码执行
```

target 的第一条用户态指令跑之前，所有限制已经落位。

## 2.顺手修的软伤

| # | 原写法 | 现写法 | 原因 |
|---|---|---|---|
| A | `OpenProcessToken(..., TOKEN_ALL_ACCESS, ...)` | `TOKEN_DUPLICATE \| TOKEN_QUERY \| TOKEN_ASSIGN_PRIMARY \| TOKEN_ADJUST_DEFAULT` | 最小权限原则：Broker 自己也该收敛 |
| B | `launch()` 里内嵌 `WaitForSingleObject(INFINITE)` | 拆出 `ProcessLauncher::WaitForExit(process, timeout, exit_code)` | Broker 不能被 target 阻塞死；后面 M3 会异步管理 |
| C | `enumerate_processes` 里 `ERROR_MORE_DATA` 判断有 bug | 用规范的**两阶段 query 循环** | 生产级Win32 API 常见模式 |
| D | HANDLE 判空只判 `INVALID_HANDLE_VALUE` | 同时判 `nullptr` 和 `INVALID_HANDLE_VALUE` | 两种"无效值"在 Win32 API 里都会出现 |
| E | 源码/字符集编码全靠猜 | CMake 显式加 `/utf-8` | 中文注释再也不会引发解析错乱 |

## 3. 分层设计要点

```
src/
├─ common/无状态工具（RAII/error/logger），任何 milestone 都能用
│  ├─ scoped_handle.h    RAII HANDLE, move-only
│  ├─ win_error.h        LastError() → std::error_code
│  └─ logger.h           线程安全宽字符 stdout 日志
├─ core/           沙箱能力砖块，各自独立可组合
│  ├─ job_manager.{h,cc}       W1: Job Object
│  ├─ token_manager.{h,cc}     W1: Restricted Token（M1 会加 IL）
│  └─ process_launcher.{h,cc}  串接 Job+Token+CREATE_SUSPENDED
└─ demo/
   └─ m0_demo.ccM0 综合验证 entry point
```

**为什么这么切**：

- `JobManager` 和 `TokenManager` **互相不认识**——每个类只做一件事。启动器 `ProcessLauncher` 是唯一"编排者"。这样 M1 加Mitigation Policy 时只改 `ProcessLauncher`，M2 加 AppContainer 时只改 `TokenManager`，M6 加 WFP 时新增 `network/wfp_engine`，**都不用改老模块**。
- `common` 是无状态的工具头文件，任何后续模块（Broker/Target/injector/payload DLL/驱动的 usermode 伙伴）都可以直接引。
- `sandbox_core` 编成 `STATIC` 库，M3 之后 Broker/Target 两个 exe 都链它。

| `CreateJobObjectW` | job_manager.cc | 建 Job 内核对象 | W1 Job Object |

| `WaitForSingleObject` / `GetExitCodeProcess` | process_launcher.cc | 等结束 + 取退出码 | 常规 |

## 5. 下一步（M1 预告）

M0 只是"权限收敛的低配版"。M1 会在**同一份 `ProcessLauncher::Launch` 里插两块**：

1. **`SetTokenInformation(TokenIntegrityLevel, S-1-16-4096)`** — Low IL。让 target 的所有内核对象访问检查从 Medium 掉到 Low，几乎所有普通桌面文件都会Access Denied。这是"沙箱味"陡然变浓的一步。
2. **`STARTUPINFOEX` + `UpdateProcThreadAttribute(PROC_THREAD_ATTRIBUTE_MITIGATION_POLICY, ...)`** — 一次装 8 项 Mitigation Policy：
   - `BLOCK_NON_MICROSOFT_BINARIES` — 反注入的绝杀
   - `PROHIBIT_DYNAMIC_CODE`
   - `CHILD_PROCESS_RESTRICTED` —沙箱标配
   - `ASLR force-relocate + bottom-up`
   - `IMAGE_LOAD_NO_REMOTE / NO_LOW_LABEL`
   - CFG / Shadow Stack（可选）

做完 M1，target 会**几乎不能干坏事**，效果非常直观。
