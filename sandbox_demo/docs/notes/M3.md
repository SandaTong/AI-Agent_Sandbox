# M3 学习笔记 — Broker/Target Named-Pipe IPC 骨架

**面试口径**：M0~M2 把 target 关进笼子（Job + Restricted Token + Low IL + Mitigation + AppContainer）。笼子越严，target 越什么都干不了——所有敏感操作必须**委托沙箱外的 broker 代劳**。M3 建立这条委托通道：一条带安全描述符授权的命名管道，broker 侧做**策略检查 + 代劳操作 + DuplicateHandle 交还句柄**。这是沙箱从"单机护栏"进化到"工程化沙箱"的关键一步——真实的 Edge renderer / Chromium 沙箱都靠这层 IPC 活着。

---

## 一、M3 在整套沙箱里的位置

```
target（沙箱内，几乎无权限）
   │  "帮我打开 C:\sandbox_share\hello.txt"   ← IPC 请求（命名管道）
   ▼
broker（沙箱外，有权限）
   │  1. 收请求
   │  2. 策略检查（路径白名单 / 拒 .. 穿越）    ← ⭐ 安全决策点
   │  3. 代劳 CreateFileW 打开
   │  4. DuplicateHandle 把句柄复制进 target    ← ⭐ 跨进程句柄传递
   ▼
target拿到句柄值，直接 ReadFile 使用
```

**核心洞见**：沙箱的价值不只在"关得严"，还在"关得严的同时仍能受控地干活"。IPC + broker 代劳就是"受控干活"的实现——**target 自己碰不到的资源，经broker 审核后可以用**。

## 二、三个技术支柱

### 支柱 1：命名管道（消息模式）

- broker：`CreateNamedPipeW(PIPE_TYPE_MESSAGE | PIPE_READMODE_MESSAGE)` → `ConnectNamedPipe`（阻塞等连接）
- target：`CreateFileW(\\.\pipe\<name>)` → `SetNamedPipeHandleState(PIPE_READMODE_MESSAGE)`
- **消息模式的价值**：一次 `ReadFile` 拿一整条消息，内核维护消息边界，省掉自己拆包/处理粘包

### 支柱 2：DuplicateHandle 跨进程句柄传递

broker 代劳打开文件后，**不能把 HANDLE 数值直接传给 target**——HANDLE 是进程私有的 handle table 索引（见 `kernel_objects_101.md` § 四）。必须：

```cpp
DuplicateHandle(GetCurrentProcess(), file,// 源：broker + 文件句柄
                target_process, &dup,           // 目标：target 进程
                0, FALSE, DUPLICATE_SAME_ACCESS);
// dup 是在 target handle table 里有效的新句柄值，通过管道回传给 target
```

**实测铁证**：broker 日志 `DuplicateHandle 到 target (dup=360)`，target 侧 `ReadFile成功，读到 30 字节`——句柄值 360 在 target 进程里直接可用，读出的字节数和 `hello.txt` 大小完全对上。

### 支柱 3：边界安全（把 target 当恶意输入）

target 是**不可信**的（可能已被攻破）。协议设计（`core/ipc_message.h`）的每一处都在防御：

- **定长头 + 变长体**，头带 `magic / version / payload_size`，收到先`ValidateHeader`
- **payload 硬上限 64KB**：target 声明 `payload_size=0xFFFFFFFF` 也不会让 broker alloc 4GB（防 DoS / 整数溢出）
- **payload_size 与实际字节数、path_chars 三者自洽校验**：绝不信任单一字段
- **路径白名单 + 拒 `..`**：防目录穿越（`C:\sandbox_share\..\..\Windows\`）
- **不透传 Win32 gle**：broker 用自定义 `ResultCode`（kOk/kDenied/...）回复，不把内部错误细节暴露给 target

## 三、实测成绩单：两条运行路径对照

M3 提供两个运行脚本，**唯一差别是 broker 命令行是否带 `--ac`**：

```
run_m3.bat:      m3_demo.exe        "hello_target.exe" --ipc
run_m3_ac.bat:   m3_demo.exe --ac   "hello_target.exe" --ipc
                            ^^^^唯一区别
```

这一个 `--ac` 决定了 target 是**普通 Low IL 受限进程**还是**AppContainer / LowBox 进程**。两条路径的 **IPC 功能完全一样**（都能连、Ping、OpenFile、DuplicateHandle），差异体现在 target 身份、管道授权方式、越狱测试结果三处。

### 两组差异对照表

| 维度 | 组 A `run_m3.bat` | 组 B `run_m3_ac.bat` |
|---|---|---|
| target 身份 | Low IL **普通受限 token** | **AppContainer / LowBox token**（有 Package SID） |
| broker 建 AppContainer profile | 不建 | 建 `com.wemeet.sandbox.demo.m3` |
| 管道 SDDL 授权 | `(SY)(BA)(WD=Everyone)` + Low label | **额外追加** `(A;;GA;;;<PackageSid>)` |
| `appcontainer=` | 0 | 1 |
| 命名空间隔离 | 无（共享 `\BaseNamedObjects\`） | 有（私有 AppContainerNamedObjects） |
| **jailbreak-4 加载非签名 DLL** | **SUCCESS**（漏） | **BLOCKED gle=5** ⭐（NTFS 层拒） |
| jailbreak-5 读剪贴板 | BLOCKED（Job UI Limit） | BLOCKED（**open 失败**，更早一层） |
| **IPC 功能（Ping/OpenFile/DupHandle）** | **全通** | **全通**（完全一样） |

### 三个决定性证据（两组都成立）

1. **`dup=360 / dup=400` + target 读到 30 字节** = DuplicateHandle 跨进程句柄传递成功（30 字节 = `hello.txt` 大小，完全对上）
2. **`hello.txt` 放行 / `hosts` 拒绝** = broker 白名单策略生效
3. **broker/target 日志实时交错** = 两进程在真实对话

### 两组差异揭示的两个核心洞见

**洞见 1：jailbreak-4 的 SUCCESS→BLOCKED = "AppContainer 拦截点上移到 NTFS 层"（M2 结论在M3 复现）**
- 组 A strict=4 没开 DLL 签名 mitigation，非签名 DLL 能加载 → SUCCESS
- 组 B 的 AppContainer Package SID 对 `unsigned_probe.dll` 所在目录**没读权限**，NTFS 层直接拒 → gle=5。**同一个机制在不同 milestone 反复出现**。

**洞见 2：AppContainer 隔离得再死，IPC 照样通（关得死但能干活）**
- 组 B的 target 是纯 AppContainer——jailbreak-6 看不到 broker 在全局命名空间造的 mutex（命名空间隔离生效）
- 但它**照样能连一条专门授权了 Package SID 的命名管道**，Ping/OpenFile/DuplicateHandle 全通
- **关键区别**：`Global\mutex` 走前缀重定向落到私有命名空间→看不到；`\\.\pipe\name` 是**显式授权 Package SID 的对象**→连得上。**target 被关到与世隔绝，只留 broker 授权的那一条通道**——这就是 Chromium renderer 的工作方式。

## 四、⭐ M3 亲踩的坑：命名管道 SDDL 的"双门"

**现象**：第一版 target（Low IL 普通 token，不带 AppContainer）连broker 管道直接 `ACCESS_DENIED (gle=5)`，IPC 段打出 `[ipc] 连接 broker 失败: gle=5`。

**排障过程**：
1. 先怀疑是 `--ipc` 参数没传到 target → 加日志打印 `cmd_line`，确认 `"hello_target.exe" "--ipc"` 传对了，排除
2. 从外部普通进程连管道也被拒 → 锁定是**管道 SD 的问题**

**根因（两层，正好复用 M1 坑 #4 的"双门"结论）**：

我第一版 SDDL 是 `D:(A;;GA;;;SY)(A;;GA;;;BA)` —— 只授权 SYSTEM + Administrators。

- **第一层门 DACL**：一旦**显式写了 DACL**，就没有"默认创建者授权"兜底了。Low IL target 的身份既不是 SYSTEM 也不是 Admin，**不匹配任何一条 ACE →拒绝**
- **第二层门 Mandatory Label**：就算 DACL 放行，管道对象默认继承创建者（broker，Medium IL）的完整性标签。Low IL target `NoWriteUp` 到 Medium label一票否决

**修法**：
```
D:(A;;GA;;;SY)(A;;GA;;;BA)(A;;GA;;;WD)[+ (A;;GA;;;<PackageSid>)]
S:(ML;;NW;;;LW)
```
- DACL 加 `(A;;GA;;;WD)`（Everyone）覆盖 Low IL 普通 target；带 AppContainer 时额外追加 Package SID
- SACL 加 `(ML;;NW;;;LW)` 把管道 mandatory label 降到 Low，让 Low IL 主体通过完整性门

**验证**：修复后从 `ACCESS_DENIED (gle=5)` → `target 已连接`。外部普通进程连管道也从"拒绝"变成"实例被占用超时"（说明有权访问，只是 target 先占了唯一实例）。

> ⚠️ **安全权衡**：demo 里DACL 放 Everyone 是为了让不带 AppContainer 的 Low IL target 也能连。**生产上不应放 Everyone**（等于把管道对全机开放，制造新攻击面），而应精确到目标进程 token 的 user SID 或 AppContainer Package SID（**最小授权原则**）。Chromium sandbox 就是精确授权到 renderer 的 token。

## 五、AppContainer target 连管道（M3 + M2 的缝合点）

带 `--ac` 时，target 是 AppContainer / LowBox token，主体是 Package SID（`S-1-15-2-...`）。broker 建管道时把 SDDL 追加一条 `(A;;GA;;;<PackageSid>)`：

```
[+] AppContainer: package SID = S-1-15-2-3048188016-...
[+] PipeServer: 管道 SD 追加授权 AppContainer SID S-1-15-2-3048188016-...
```

**这一步把 M2 的 AppContainer 和 M3 的 IPC 缝在一起**——没有这条 ACE，AppContainer target 连管道必然 `ACCESS_DENIED`。这也是"我真做过沙箱 IPC"最硬的证明点：**知道 AppContainer 进程连内核对象需要在对象 SD 上显式授权 Package SID**。

**对照实验**（教学用）：把 `pipe_server.cc` 里授权 Package SID 那段去掉重编，AppContainer target 就会打`[ipc] 连接 broker 失败: gle=5`——直接的"未授权 SID"证据。

## 六、代码结构

| 文件 | 角色 | 关键点 |
|---|---|---|
| `core/ipc_message.h` | 协议 | 定长头 + payload 上限 + magic/version 校验 + `#pragma pack` + static_assert |
| `core/pipe_server.{h,cc}` | broker 侧 | SDDL 双门授权 + 消息收发 + 路径白名单 + DuplicateHandle |
| `core/pipe_client.{h,cc}` | target 侧 | 连管道 + 发请求收响应；`ACCESS_DENIED` 即授权未生效的直接信号 |
| `demo/m3_demo.cc` | broker demo | 建管道(授权) → launch → WaitForClient → 服务循环 |
| `demo/hello_target.cc` | target | `--ipc` 触发 `RunIpcClientDemo` |

**服务循环的生命周期**：broker `WaitForClient` 等target 连上→ 循环 `ServeOneRequest` → target 跑完 IPC demo 进心跳不再发消息 → broker `ReadFile` 得 `ERROR_BROKEN_PIPE` → 优雅退出服务循环 → 继续等 target 退出。

## 七、面试话术合集

### 话术 A：为什么沙箱需要 IPC（沙箱哲学）

> "沙箱的价值不只在'关得严'，还在'关得严的同时仍能受控地干活'。M0~M2 我把 target 关进 Job + Restricted Token + Low IL + AppContainer，它几乎什么都干不了——连读一个文件都做不到。但真实的 renderer 是要渲染网页的，它必须能读字体文件、发网络请求。矛盾的解法就是 IPC + broker 代劳：target 把敏感操作**委托**给沙箱外的 broker，broker 做**策略检查**后代劳，再把结果（比如文件句柄）交还给 target。**broker 成了唯一的安全决策点**——所有越权尝试都收敛到 broker 一个地方审核。Chromium 的 renderer/browser 进程模型就是这套。"

### 话术 B：DuplicateHandle 与"HANDLE 是进程私有索引"

> "M3 里 broker 代劳打开文件后要把句柄交给 target，我一开始的直觉是把 HANDLE 数值通过管道发过去——这是错的。HANDLE 不是内核对象指针，而是**当前进程 handle table 的索引**，进程私有。target拿到 broker 的索引值在自己的 handle table 里查是查不到的。正确做法是 `DuplicateHandle`——让内核在 target 进程的 handle table 里新建一个指向同一内核对象的表项，返回的新句柄值才在 target 那边有效。实测 broker 打开的文件在 target 里变成句柄值 360，target 直接 `ReadFile(360)` 读到了正确内容。**这印证了 HANDLE 的本质：不是指针，是进程私有的 handle table 索引，跨进程共享内核对象必须走DuplicateHandle**。"

### 话术 C：命名管道 SDDL 的双门（M3 亲踩，复用 M1 坑 #4）

> "M3 我踩了一个和 M1 桌面隔离同源的坑。Low IL target 连 broker 管道被 `ACCESS_DENIED`。排查发现是管道 SD 的问题——而且是**双层**：第一层，我显式写了 DACL 只授权 SYSTEM 和 Admin，一旦显式写 DACL 就没有默认的创建者授权兜底了，Low IL 普通 token 不匹配任何 ACE 被拒；第二层，就算 DACL 放行，管道对象默认继承创建者 Medium IL 的 mandatory label，Low IL target NoWriteUp 到 Medium label 又被一票否决。修法是 DACL 加目标主体的授权（Everyone 或精确到 Package SID）+ SACL 加一条 `(ML;;NW;;;LW)` 把管道完整性门槛降到 Low。**这正好复用了我M1 桌面隔离时理解的'Windows 访问检查是 DACL AND Mandatory Label 双门'结论——同一套安全模型在管道对象上再次出现**。生产上 DACL 不该放 Everyone，要精确到目标进程 token 或Package SID，最小授权。"

### 话术 D：不可信输入的边界安全

> "写 broker 的 IPC 处理时，我把 target 当**恶意输入**处理——它可能已经被攻破。协议头里带 magic、version、payload_size，收到第一步 `ValidateHeader`。payload 有64KB 硬上限，target 就算声明 payload_size 是 4GB，broker 也不会真去 alloc，防DoS 和整数溢出。变长路径请求里 path_chars 必须和 payload_size 自洽——绝不信任单一字段。路径做白名单前缀匹配 + 拒绝含 `..` 的穿越。broker 回复用自定义 ResultCode 而不是透传 Win32 gle，避免把内部错误细节泄露给 target。**这些都是沙箱 IPC 最经典的攻击面，一个memcpy 信任了target 给的长度就可能被打穿**。"

## 八、下一步（M4 预告）

M3 的 broker 现在只服务一个 target、单线程阻塞、只有 OpenFile 一种请求。M4/M5 会扩展：
- 多 target 并发（IOCP / 线程池）
- 更多 broker 服务（网络请求代劳 → 接 M2 的 firewall /未来的 WFP）
- 策略引擎独立化（当前白名单是硬编码前缀，未来做成可配置规则表）
