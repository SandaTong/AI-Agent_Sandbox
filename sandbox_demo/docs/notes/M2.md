# M2：AppContainer + Capability 白名单（LowBox Token）

> 面向面试的**知识密度笔记**。前置：M0（Job + Restricted Token）、M1（Low IL + Mitigation + Alt Desktop）。

## 一、AppContainer 一句话讲清

**AppContainer = 独立 Package SID + 独立对象命名空间 + Capability 白名单**。UWP / Windows Store 应用、Edge renderer、Windows Sandbox 都是这一套。

三个核心概念：

1. **AppContainer Profile**：`CreateAppContainerProfile(名字, 显示名, 描述, capabilities, ...)` 在系统里注册一份 profile，产生一个**独一无二的 Package SID**（`S-1-15-2-<8个整数>`）。同名 profile 只保留一份（幂等）。
2. **Package SID**：target 进程的主体 SID 从"你的用户 SID"变成这个 Package SID。此后**所有的访问检查**都走 LowBox 路径。
3. **Capability SID**：AppContainer target 默认几乎啥都做不了——想干什么必须**显式声明** capability（`internetClient` / `documentsLibrary` / `picturesLibrary` /自定义）。Well-known cap 有对应的 `WinCapabilityInternetClientSid` 等 `WELL_KNOWN_SID_TYPE`。

## 二、LowBox Token 是怎么诞生的

**关键 API**：`CreateProcessW` + `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` 属性。

```c
SECURITY_CAPABILITIES sc{};
sc.AppContainerSid = <package sid>;
sc.Capabilities    = <cap sid[]>;   // SID_AND_ATTRIBUTES 数组
sc.CapabilityCount = <n>;

UpdateProcThreadAttribute(
    attr_list, 0,
    PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES,
    &sc, sizeof(sc), nullptr, nullptr);
```

内核识别到这个属性后，会在 `CreateProcess` 内部做几件事：

1. 从 caller 的 primary token 派生出一个 **LowBox Token**（`TokenInformationClass::TokenIsAppContainer = TRUE`）
2. 把 primary user SID 换成 Package SID
3. 把 capability SIDs 加进 groups 列表
4. Mandatory Label 强制降到 Low（AppContainer 天然 Low IL）
5. token 上打 `TOKEN_LOWBOX` 标记 → 后续访问检查走 LowBox 路径

结果：target 拿到的 token 属于**独立完整性域 + 独立主体 + 独立命名空间**。

## 三、AppContainer 的对象命名空间隔离

**这是 AppContainer 招牌效果**：

| 对象类型 | 普通进程看到 | AppContainer 看到 |
|---|---|---|
| Named Mutex/Event | `\BaseNamedObjects\Foo` | `\Sessions\<n>\AppContainerNamedObjects\<pkg_sid>\Foo` |
| Named Pipe | `\Device\NamedPipe\Foo` | 私有 pipe 空间 |
| WinStation | `WinSta0` | AppContainer 自己的 winsta |
| Registry | `HKCU\Software\...` | `HKCU\Software\Classes\Local Settings\Software\Microsoft\Windows\CurrentVersion\AppContainer\Storage\<pkg>\` |
| 文件系统 | 用户 profile 完全可读 | 默认只有 AppContainer 自己的目录 |

对 target来说：**它看到的世界，是一个"从零 populate的私有命名空间"**——就算你broker 提前创建了名字叫 `\BaseNamedObjects\ShimCacheMutex` 的对象，target `OpenMutexW(L"Global\\ShimCacheMutex")` 返回 `ERROR_FILE_NOT_FOUND (2)`，因为**它的 `Global\\` 前缀根本不指向那里**。

## 四、Capability 白名单机制

target 默认几乎啥都做不了。想干什么就**显式带上对应的 capability**：

| Capability | Well-Known SID | 允许做什么 |
|---|---|---|
| `internetClient` | `WinCapabilityInternetClientSid` | 出方向网络（TCP/UDP connect） |
| `internetClientServer` | `WinCapabilityInternetClientServerSid` | 出+入方向网络 |
| `privateNetworkClientServer` | `WinCapabilityPrivateNetworkClientServerSid` | 内网访问 |
| `documentsLibrary` | `WinCapabilityDocumentsLibrarySid` | 用户Documents 目录 |
| `picturesLibrary` | `WinCapabilityPicturesLibrarySid` | 用户 Pictures 目录 |
| `musicLibrary` / `videosLibrary` | 类似 | 音乐 / 视频目录 |
| 自定义 | `DeriveCapabilitySidsFromName` 派生 | 自定义资源授权 |

**Capability 是"加法"**：不加就默认禁；加了对应 cap，内核在做那一类资源的访问检查时才允许放行。**面试话术**：AppContainer 是**默认拒绝**的白名单模型，比 Restricted Token 的**默认允许-显式撤销** privilege 模型精确得多。

```
[+] AppContainer: package SID = S-1-15-2-3985501692-...
[+] MitigationAttrList: 已装配 ... appcontainer=1
[target] integrity_level=Low
[jailbreak-1] 写用户桌面文件 : BLOCKED (gle=5)     ← Low IL + Package SID 无授权
[jailbreak-2] 起子进程 cmd.exe : BLOCKED (gle=367)  ← CHILD_PROCESS_POLICY
[jailbreak-3] 分配 RWX 内存    : BLOCKED (gle=1655) ← PROHIBIT_DYNAMIC_CODE
[jailbreak-4] 加载非签名 DLL   : BLOCKED (gle=5)    ← 早一层：NTFS 层直接拒
[jailbreak-5] 读剪贴板: BLOCKED (gle=5, open 失败)  ← 早一层：连 OpenClipboard 都拒
[jailbreak-6] 打开global mutex : BLOCKED (gle=2)   ← ⭐ AppContainer 命名空间隔离
[jailbreak-7] TCP loopback     : SUCCESS (10061)   ⚠️ **AppContainer 单靠自身不禁网**，见 § 九
```

**关键对比：M1 vs M2 的差异点**

| 越狱 | M1 结果 | M2 结果 | M2 的拦截点为什么更早/更硬 |
|---|---|---|---|
| jailbreak-4 加载非签名 DLL | `gle=577INVALID_IMAGE_HASH` | `gle=5 ACCESS_DENIED` | M1 是 mitigation 层的 Authenticode 校验，M2 是 NTFS 层直接拒读 DLL 文件（Package SID 对该目录没授权），**更早一层拦下** |
| jailbreak-5 读剪贴板 | `GetClipboardData` 被 UI Limit 拦 | 连 `OpenClipboard` 都拒 | M2 主体不属于 winsta 剪贴板 ACL，**根本没资格打开** |
| jailbreak-6 broker 造的 global mutex | SUCCESS（共享 `\BaseNamedObjects\` 能看到 broker 造的 mutex） | `gle=2 FILE_NOT_FOUND`（**broker 明明造了，target 就是看不到**） | M2 的 `Global\` 前缀映射到私有 `\Sessions\<n>\AppContainerNamedObjects\<pkg_sid>\`，broker 的对象不在这个命名空间里 |
| jailbreak-7 网络 (loopback) | SUCCESS（M1 完全不禁网） | **仍 SUCCESS** ⚠️ | AppContainer 单独**不禁网**——网络策略全在 Windows Firewall 用户态规则表里，需要 broker 单独写规则。见 § 九 |

## 六、亲踩的坑：AppContainer 和 Alt Desktop 冲突

**表现**：M2 首次运行开着 alt desktop，target 报 `0xC0000142 STATUS_DLL_INIT_FAILED`。

**排障**：`--no-desk` 关掉 alt desktop 后立刻正常。

**根因**：AppContainer target 内核层会**自动住进** `\Sessions\<n>\AppContainerNamedObjects\<pkg_sid>\` 下自己的 winsta 命名空间。此时 `STARTUPINFO::lpDesktop` 指向的 `sandbox_winsta_xxx\sandbox_desk`（我们 M1 手工建的）**不在 AppContainer 的命名空间下**，target user32 尝试 attach 时找不到对应 desktop 对象，DllMain 失败，报 `STATUS_DLL_INIT_FAILED`。

**修法**：**M2 默认关掉 alt desktop**——AppContainer 已经把 UI 层也隔离了，不需要再手工做 alt desktop。**Chromium sandbox 的 AppContainer 分支同样不做 alt desktop**，就是这个原因。

**面试话术**：

> "M2 里我踩到 AppContainer 和手工 alt desktop 的命名空间冲突。AppContainer target 内核层会自动把自己塞进 `\Sessions\<n>\AppContainerNamedObjects\<pkg_sid>\` 下的私有 winsta，我们 M1 手工建的 alt desktop 住在传统 `WinSta0` 命名空间下——target user32 DllMain 里 `NtUserOpenDesktop` 根本找不到那个 desktop，报 `STATUS_DLL_INIT_FAILED`。**教训是：AppContainer 已经提供命名空间级的 UI 隔离，不要再叠加 alt desktop——Chromium sandbox 也是这样处理的**。UI 隔离在三种手段里：Job UI Limit / Alt Desktop / AppContainer，选一个即可。"

## 七、`BLOCK_NON_MICROSOFT_BINARIES` 在 M2 里要关掉

**踩坑**：M2 里如果继续开 `BLOCK_NON_MICROSOFT_BINARIES` (`strict_signed_dll=true`)，target 挂在加载 winsock helper (`mswsock.dll` 等) 时——这些 DLL 在 AppContainer 命名空间下加载走特殊路径，会拉进不带微软根签名的组件。

**修法**：M2 里主动把 `strict_signed_dll = false`。反正 AppContainer 已经把加载非签名 DLL 的效果做出来了（jailbreak-4 依旧 BLOCKED，只是拦截点从 mitigation 层变成 NTFS 层）。

## 八、Package SID 的 UI 观察（实测校准版）

跑起来 M2 target 后：

### Process Explorer → hello_target → Properties → Security 页

**⚠️ 反常识观察**（第一次看会以为沙箱没生效）：

- **顶部 User: `TENCENT\<你>`** —— **依然是你的域账号名**！Process Explorer 显示的是 token 的 `TokenUser` 字段，AppContainer 不会改变这个字段（LowBox token 是**在你的用户 token 之上叠加 Package SID 作为 group**，不是替换 primary user）。第一次看会以为沙箱没生效——**不是这样**，往下看 Group 列表
- **顶部 SID: `S-1-5-21-...`** —— 同样是你的域账号 SID

**真正的 AppContainer 证据在 Group 列表里**：

```
TENCENT\c_xxx(你的域组)   ← 你的域账号自带
S-1-15-2-<8个整数>     ← ⭐⭐⭐ Package SID，Flags 一栏显示 `AppContainer`（不是 `Mandatory`）
NT AUTHORITY\This Organization               ← 域账号自动带
NT AUTHORITY\LogonSessionId_0_xxxxxxxx           ← 登录会话 SID
NT AUTHORITY\INTERACTIVE
NT AUTHORITY\Authenticated Users
Mandatory Label\Low Mandatory Level  ⭐          ← M1 层的 Low IL 也在
LOCAL / Everyone / CONSOLE LOGON / BUILTIN\Users / ...
```

**关键读法**：
- **`S-1-15-2-...` 那一行是 Package SID**，作为 group 加进 token —— 之后所有访问检查内核走 LowBox 路径
- **⭐ 放大窗口看这行右边 Flags 一栏 = `AppContainer`**（其他 group 全部是 `Mandatory`），这是 **LowBox Token 存在的内核实证**——普通进程或 M1 target 的 token 里根本不会有一条 SID 带 `AppContainer` flag。内核 `SeAccessCheck` 看到这个 flag 就走 AppContainer 三层访问检查（DACL + Mandatory Label + Capability）而非普通两层
- **`Mandatory Label\Low Mandatory Level` 那一行是 M1 的产物** —— 我们代码里主动 `SetIntegrityLevel(Low)`

**深水区问题：为什么不是 `Mandatory Label\AppContainer Level`？**

纯 UWP App 的 token 完整性标签是 `AppContainer Level` (SID `S-1-16-0` 之类的独立完整性域)——比 Low IL 还低一档。我们的实现主动调 `SetIntegrityLevel(Low)`，然后 `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` 让内核派生 LowBox token 时 Package SID 加进 Groups 但 IL 保持 Low。所以 target 是**"Low IL + AppContainer Package SID" 的混合态**，不是纯UWP 的AppContainer IL。

对越狱防护来说这种混合态已经完全够用（jailbreak-1~7 全 BLOCKED）；想做到"完全 UWP 级"需要跳过 `SetIntegrityLevel` 让内核自动降到 AppContainer IL。**这是 M2 未做的一件事，也是从 dev-mode Sandbox 演进到"真正 UWP 品质"的 gap**。

### WinObj → `\Sessions\<你的Session>\AppContainerNamedObjects\`（内核层证据）

用 Sysinternals **WinObj**（管理员启动），左侧树浏览到 `\Sessions\<n>\AppContainerNamedObjects\`，会看到系统里**每一个 AppContainer profile 都对应一个 `S-1-15-2-...` 子目录**——包括 Windows 内建的 UWP App / Edge renderer / Store App，以及我们的 `com.wemeet.sandbox.demo.m2`（跟 broker 日志里那串 SID 一一对上）。

**打开我们的 profile 目录，右侧会看到 5 个对象**（真实截图记录）：

| Name | Type | Target |
|---|---|---|
| **Local** | **SymbolicLink** | `\Sessions\1\AppContainerNamedObjects\S-1-15-2-...`（**指向自己**） |
| **Session** | **SymbolicLink** | 同上 |
| `SM0:<pid>:304:WilStaging_02_p0` | Semaphore | target 起来时 CRT 自动造 |
| `SM0:<pid>:304:WilStaging_02_p0h` | Semaphore | 同上 |
| `SM0:<pid>:304:WilStaging_02` | Mutant | 同上 |

**⭐⭐⭐ `Local` 和 `Session` 是 SymbolicLink** —— **这是命名空间隔离机制的物理实现**：target 代码里写 `Local\Foo` 或 `Session\Foo`，内核 Object Manager (`nt!ObpLookupObjectName`) 走这两条符号链接落到私有命名空间根，**target 完全无感知**。同理，target 写 `Global\WEMEET_SANDBOX_PROBE_MUTEX` 时内核会把 `Global` 前缀重定向到这里（**AppContainer 特殊路径**），**找不到 broker 造的对象** → `FILE_NOT_FOUND (gle=2)`。

**对比 broker 造的 mutex 实际住在哪**（WinObj 里从根目录直接看）——

**Windows 有两个 BaseNamedObjects，区别于层级和访问范围**：

| 目录 | 生存期 | 谁能看到 | broker 写什么前缀落这里 |
|---|---|---|---|
| **`\BaseNamedObjects\`**（根目录） | **全局 session-independent** | 系统所有进程 | `Global\Foo` |
| **`\Sessions\<n>\BaseNamedObjects\`** | 每 Session 独立 | 同 Session 的普通进程 | `Local\Foo`（或不带前缀，Vista+ 默认走 per-session）|

**broker 里我们写的是 `L"Global\\WEMEET_SANDBOX_PROBE_MUTEX"`** → 落到根 `\BaseNamedObjects\WEMEET_SANDBOX_PROBE_MUTEX`（**WinObj 从左边树根节点直接展开BaseNamedObjects 就能看到**）。

**这就是 jailbreak-6 gle=2 (FILE_NOT_FOUND) 完整的物理证据链**（WinObj 里能同时看到两个端点）：

```
端点 A（broker 造的）：
    \BaseNamedObjects\WEMEET_SANDBOX_PROBE_MUTEX   ✅ 存在（Type: Mutant）

端点 B（target 眼里的）：
    \Sessions\1\AppContainerNamedObjects\<pkg_sid>\
        Local  (SymbolicLink → 自己)
    Session   (SymbolicLink → 自己)
        SM0:...:WilStaging_02_*(CRT 自动造的)
    ❌ 没有 WEMEET_SANDBOX_PROBE_MUTEX
```

target 写 `OpenMutexW(L"Global\\WEMEET_SANDBOX_PROBE_MUTEX")`：
1. 内核检测到 target 是 AppContainer
2. `Global` 前缀被 hook 到 target 私有命名空间根（**不再指向根 `\BaseNamedObjects\`**）
3. 私有命名空间里没有这个 mutex → `FILE_NOT_FOUND`

**这是 Windows 沙箱最优雅的一层设计**——AppContainer 命名空间隔离不需要 target 侧任何配合，全部是内核 Object Manager 层的**前缀劫持 + 符号链接重定向**。target 以为在跟 broker 说话，实际内核把它的世界完全重定向了。**内核实现细节见 [`kernel_objects_101.md`](kernel_objects_101.md) § 七（命名空间树 + 前缀劫持）**。

### AppContainer 的三种前缀重定向规则（沉淀）

| target 代码写的 | 普通进程解析到 | AppContainer target 解析到 |
|---|---|---|
| `Global\Foo` | `\BaseNamedObjects\Foo`（全局） | `\Sessions\<n>\AppContainerNamedObjects\<pkg>\Foo`（私有） |
| `Local\Foo` | `\Sessions\<n>\BaseNamedObjects\Foo`（同 session） | `\Sessions\<n>\AppContainerNamedObjects\<pkg>\Local\...` → **符号链接指回自己**，即私有 |
| `Session\Foo` | 同 Local | 同 Local |
| 不带前缀`Foo` | `\Sessions\<n>\BaseNamedObjects\Foo`（同 session, Vista+ 默认） | 私有 |

**任何写法都会被内核劫持到私有命名空间**——这就是"target 侧无感知，看到的世界完全被内核换了"。

### 顺便：面试话术 F（WinObj 实测题）

> "AppContainer 命名空间隔离**不是靠 target 进程侧走特殊代码**实现的，而是**内核在 Object Manager 层做前缀劫持 + 符号链接重定向**。用 WinObj 展开 `\Sessions\<n>\AppContainerNamedObjects\<pkg_sid>\` 目录能看到里面预置了两个 SymbolicLink 对象 `Local` 和 `Session`——target 写 `Local\Foo` 或 `Session\Foo` 时内核 `ObpLookupObjectName` 走符号链接直接落到私有命名空间根。**更关键的一步是 `Global\` 前缀被内核劫持**——普通进程写 `Global\Foo` 会落到根 `\BaseNamedObjects\`（全局 session-independent 的目录），但 AppContainer target 写同样的字符串会被内核重定向到自己的私有命名空间根。我 M2 里 broker 在根 `\BaseNamedObjects\` 造了一个探测 mutex，target 用同一个 `Global\Foo` 名字打开——**broker 的对象明明存在**（WinObj 能看到），**target 就是 FILE_NOT_FOUND**，因为它俩落的根本不是同一个命名空间。**这个观察让我理解了 AppContainer 隔离机制的优雅之处——target 不需要任何配合，内核 Object Manager 就把它的世界完全重定向了**。也让我理解了 Windows 里 `Global\` / `Local\` / `Session\` 这三个前缀在普通进程和 AppContainer 里的语义差异——一套字符串，两套解析规则。Chromium sandbox 的 AppContainer 分支能拿 UWP 隔离级别当免费午餐，就是靠这层内核魔法。"

## 九、⚠️ 校准过后的结论：AppContainer 网络策略实际上是"纸老虎"

**实测事实**（M2 亲跑，见broker+target 输出）：

```
[+] AppContainer: package SID = S-1-15-2-...← Package SID 有了
[+] MitigationAttrList: ... appcontainer=1            ← LowBox 属性上了
[target] integrity_level=Low                          ← target 确实是 AppContainer
  [jailbreak-6] 打开 global mutex : BLOCKED (gle=2)   ← 命名空间隔离生效
  [jailbreak-7] TCP loopback     : SUCCESS(10061)   ← ❌ 网络照样通！
```

**target 是纯AppContainer，命名空间隔离都生效了，但 `127.0.0.1:1` 的 TCP SYN 照常发到内核网络栈，返回正常的 `WSAECONNREFUSED (10061)`——1 号端口没人listen 是真话，但整个访问路径根本没进 sandbox 检查**。也就是说AppContainer 单独存在时，**根本没禁掉网络出方向**。

### 我最初的错误认知

我最初写笔记时以为 AppContainer 的网络策略分两层，其中 L1 是 "WFP内核 `AppContainerLoopback` 过滤器硬拦回环出方向"。**实测证明这个理解是错的**：

- ✅ `AppContainerLoopback` 过滤器确实存在，但它只拦**入方向 (INBOUND)**——防止本机其他进程连 AppContainer 内进程的 listen socket 做 IPC 逃逸
- ❌ **出方向 (OUTBOUND) loopback 和公网走完全同一条路径**——都依赖 Windows Firewall 用户态规则引擎

### 真正的机制：网络策略完全依赖 Windows Firewall 用户态规则

- 位置：`mpssvc` 服务 + 用户态防火墙规则表
- 判定：AppContainer target 发起 TCP connect 时，`FWPM_LAYER_ALE_AUTH_CONNECT_V4` 层查规则表 → 有匹配 Package SID 的 block 规则就拦，否则走各 profile 的 `DefaultOutboundAction`（大多数开发机是 `NotConfigured` = Allow）
- capability 的角色：**capability SID 只是规则的匹配标签**（"这条规则针对哪些 AppContainer 生效"），**规则本身要有人写**

### 为什么 UWP App 能被防火墙拦住而我们不行

`Add-AppxPackage` 部署 UWP 时：
1. 解析 AppxManifest.xml 里的 `<Capabilities>` 声明
2. 框架**自动往 Windows Firewall 写规则**：一条outbound "block all"（针对该Package SID）+ 若干 allow 规则（比如 `internetClient` cap 对应一条 outbound TCP allow）

我们用 `CreateAppContainerProfile` 只落地 Registry `\HKCU\...\AppContainer\Storage\<pkg>\`，**没有任何一步会自动写防火墙规则**——这是纯手工 profile 和 UWP 部署的根本差异。

### 结论：M2 单独存在时只能证明"命名空间隔离"

- ✅ **命名空间隔离** = AppContainer 真正的杀器 —— jailbreak-6 实证
- ⚠️ **网络策略** = 纯粹是防火墙规则表的事，AppContainer 单靠自己**不禁网** —— jailbreak-7 实证
- 想让 target 真禁网，broker 必须**主动往 Windows Firewall 写一条 outbound block 规则**

这就是 M2 "加餐补丁"要做的事：新增 `core/firewall.{h,cc}` 用 `INetFwPolicy2` COM API 加规则。做完之后 jailbreak-7 才会真的 BLOCKED。见下方 § 十一"加餐"。

### 面试金牌话术：AppContainer 不等于自动禁网

> "M2 我拿到了一个非常反直觉的实测结论：**AppContainer 单靠自身不禁网**。target 是纯 AppContainer、命名空间隔离都生效了，但打 `127.0.0.1:1` 的 SYN 照样发到内核网络栈，正常返回 `WSAECONNREFUSED`。这颠覆了我一开始的认知——我原以为 AppContainer 里有个 `AppContainerLoopback` 内核过滤器硬拦回环，后来才发现那个过滤器只对入方向生效。真相是：**AppContainer 的网络策略完全依赖 Windows Firewall 用户态规则引擎**，capability 只是规则的匹配标签，规则本身要有人写。UWP App 通过 `Add-AppxPackage` 部署时框架会自动写规则；我们用 `CreateAppContainerProfile` 手工建 profile 只落地 Registry，不会写规则，所以 target 直连出方向就漏了。生产级实现要 broker 起 target 前程序化调 `INetFwPolicy2` COM API 补齐规则，Chromium sandbox 就是这么做的——M2 加餐补丁我实现了这一步。**这个教训告诉我：Windows 沙箱的每一层都必须实测验证，不能'因为 API 名字看起来威力大就默认它能拦'**。"

## 十、面试话术合集

### 话术 A：AppContainer 三件套

> "AppContainer 由三件东西组成：**Package SID + 独立命名空间 + Capability 白名单**。Package SID 是通过 `CreateAppContainerProfile` 注册出来的，形如 `S-1-15-2-<8个整数>`，target 的主体从'你的用户 SID'变成这个 SID 后，所有访问检查走 LowBox 路径。独立命名空间指 target 看到的 `\BaseNamedObjects\` 实际映射到 `\Sessions\<n>\AppContainerNamedObjects\<pkg_sid>\`，看不到 global 对象。Capability 白名单是精确授权模型：默认几乎啥都做不了，想干什么就带对应 capability——比如 `internetClient` 允许出方向网络，`documentsLibrary` 允许访问用户 Documents 目录。这是**默认拒绝**的白名单模型，比 Restricted Token 的**默认允许-显式撤销** privilege 模型精确得多。"

### 话术 B：LowBox Token 的内核层理解

> "LowBox Token 是通过 `CreateProcess` 时传 `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` 让内核派生出来的。内核识别到这个属性后会做几件事：从 caller primary token 派生 LowBox token、**把 Package SID 作为 group SID 追加到 TokenGroups**（**不是替换 TokenUser**，见话术 B'）、capability SIDs 加进 groups、token 打 `TOKEN_LOWBOX` 标记。之后 target 的每次 `SeAccessCheck` 都走 AppContainer 专用路径——不是普通的 DACL 检查加 Mandatory Label 检查那两层，而是**三层**：DACL + Mandatory Label + Capability。这是 Windows 安全模型的最完整形态。"

### 话术 B'：LowBox Token 是"叠加态"不是"替换态"（Process Explorer 实测惊喜）

> "M2 我用 Process Explorer 看target 的 token 时踩过一个反直觉的坑——**Security 页顶部的 User 一栏依然是我的域账号名 `TENCENT\<user>`**，第一次看会以为 AppContainer 没生效。但实际上 AppContainer 生效的证据在 Group 列表里——**Package SID (`S-1-15-2-...`) 是作为一条 group SID 追加进 token，不是替换 primary user**。**放大 Process Explorer 窗口能看到这条 SID 右边的 Flags 栏是 `AppContainer`**（其他所有 group 都是 `Mandatory`），这个 flag 是 Windows 内核 token 结构里 `SE_GROUP_LOGON_ID | SE_GROUP_INTEGRITY` 之类特殊组合位的字符串化——**只有真正的 LowBox Token 才会有一条 SID 带这个 flag**。内核的 `SeAccessCheck` 优先看这个 flag 而不是 `TokenUser`，自动走 AppContainer 三层访问检查路径。**这个坑教我一件事：token 结构里显示的字段和实际访问检查使用的字段不一样**——想真正验证沙箱要看 Group 列表里那一行的 Flags，不是看 User 字段。也让我理解了 LowBox Token 的**叠加态**本质：TokenUser 保留、Package SID 追加、通过 flag 位切换主体身份。"

### 话术 C：为什么 jailbreak-4 从 M1 的 gle=577 变成 M2 的 gle=5

> "M1 里加载非签名 DLL 报 `gle=577 (INVALID_IMAGE_HASH)`，M2 里变成 `gle=5 (ACCESS_DENIED)`——同一个越狱动作，M2 的拦截点比 M1 更早一层。M1 是 mitigation policy 在**加载器映射映像时**做 Authenticode 校验，M2 是 **NTFS 层直接拒读 DLL 文件本身**——因为 Package SID 对 `unsigned_probe.dll` 所在目录压根没读权限，走不到 mitigation 层。这个观察很有意义：**沙箱是一层套一层的，越靠外层拦下越好**——AppContainer 是最外层，很多 mitigation 在它面前变得冗余。这也是为什么现代 Chromium renderer 里 mitigation 的严格程度反而没M1 那么极端，因为 AppContainer 已经把很多路径堵死了。"

### 话术 D：AppContainer vs Alt Desktop 冲突（M2 亲踩的坑）

> "M2 我踩过一个坑：AppContainer 和手工 alt desktop 命名空间冲突，target 报 `0xC0000142`。原因是 AppContainer target 内核层会自动塞进 `\Sessions\<n>\AppContainerNamedObjects\<pkg_sid>\` 下自己的 winsta，而 M1 手工建的 alt desktop 住在传统 `WinSta0` 命名空间下——target user32 DllMain 里 `NtUserOpenDesktop` 根本找不到。**教训**：UI 隔离的三种手段（Job UI Limit / Alt Desktop / AppContainer）互斥，选一个即可。Chromium sandbox 的 AppContainer 分支就不做 alt desktop。这也告诉我们**沙箱不是把所有可能的机制都堆上去就是最强**，机制之间有相互作用，要理解每一层做什么再选。"

## 十一、加餐补丁：`INetFwPolicy2` 程序化写 Windows Firewall 规则

M2 § 九 揭示了"AppContainer 单靠自身不禁网"这个反直觉结论。补丁做的事：**broker 起 target 前，程序化调`INetFwPolicy2` COM API 加一条针对 target Package SID 的 outbound TCP block 规则**。target 退出后 broker 析构里自动 `RemoveRule`，防火墙不留污染。

### 代码骨架

新文件 `src/core/firewall.{h,cc}`：

```cpp
FirewallGuard fw;
fw.AddBlockAllOutboundForAppContainer(
    package_sid_sddl,             // "S-1-15-2-..."
    L"sandbox_demo_m2_block_outbound");   // 规则名
```

内部三步：
1. `CoInitializeEx(APARTMENTTHREADED)` 起 COM
2. `CoCreateInstance(CLSID_NetFwPolicy2)` 拿 policy → `get_Rules` 拿规则集合
3. `CoCreateInstance(CLSID_NetFwRule)` 造一条规则 → QI 成 **`INetFwRule3`**（Win8+ 才加的接口，是它有 `put_LocalAppPackageId`）→ 设 Direction=Out / Action=Block / Protocol=6 (TCP) / Package SID → `rules->Add()`

### 关键坑：`INetFwRule2` vs `INetFwRule3`

我一开始 QI 到 `INetFwRule2`，编译报 `C2039 "put_LocalAppPackageId" 不是 "INetFwRule2" 的成员`。查 SDK：

- `INetFwRule2` (Win7+) 只加了 `EdgeTraversalOptions`
- `INetFwRule3` (Win8+) 才加了 AppContainer 相关的 `LocalAppPackageId` / `RemoteMachineAuthorizedList` 等属性

**教训**：Windows COM 接口版本升级采取"新接口继承老接口"模式，`INetFwRule3 : INetFwRule2 : INetFwRule`。想用某个新属性必须 QI 到最新版本的接口。

### 实测结果三档（管理员权限）

Firewall 规则加进系统后可用 `Get-NetFirewallRule -DisplayName sandbox_demo_m2_block_outbound` 查证；`Get-NetFirewallApplicationFilter` 能看到 `Package = S-1-15-2-...` 绑定。

| 场景 | Firewall 规则 | jailbreak-7 (TCP 8.8.8.8:80) |
|---|---|---|
| 基线(baseline) | 无 | **SUCCESS** (SYN 出去到公网) |
| M2 默认（管理员） | outbound block 规则 in system | **BLOCKED** (WSAErr=10013 或被上游企业代理拦，见下) |
| M2 --net（管理员） | broker 跳过加规则 | **SUCCESS** (WSAErr=0 真连上 Google DNS) |
| M2 默认（非管理员） | broker 加规则失败(E_ACCESSDENIED)，只警告 | **SUCCESS** —沙箱漏 |

### 坑 X：Loopback bypass

第一版 jailbreak-7 打 `127.0.0.1:1`，即使加了 Firewall 规则仍然 SUCCESS。**根因**：Windows Firewall 对 loopback (127.0.0.1/8, ::1/128) 流量默认 bypass 规则匹配 —— 这是 mpssvc 的内建行为，跟规则表无关。想拦 loopback 得走别的机制（例如自己写 WFP callout driver）。

**校准后的实践**：jailbreak-7 必须打**公网 IP** (8.8.8.8) 才能验证 Firewall 规则的效果。

### 🟢 这笔"loopback 债"已在 M6 还清

M6 用 **WFP 用户态 filter** 挂在 `FWPM_LAYER_ALE_AUTH_CONNECT_V4` 层——**loopback 出方向连接也走这层**，因此 M6 的 **AppID 形态**（`m6_appid_demo.cc`，按 exe 路径精确拦 target 全部 outbound）实测把 `[7c] 127.0.0.1` 也拦下了（`WSAErr=10013`），补上了本节留的债：

```
[7a] 8.8.8.8   : BLOCKED (WSAErr=10013)
[7b] 1.1.1.1   : BLOCKED (WSAErr=10013)
[7c] 127.0.0.1 : BLOCKED (WSAErr=10013)  ⭐ M2 Windows Firewall 拦不了的 loopback，M6 WFP 拦下了
```

- **为什么 WFP 能拦而 Firewall 不能**：Firewall 是 WFP 的上层应用，且对 loopback 默认 bypass 规则匹配；WFP 直接挂 ALE 连接授权层，loopback 也经过该层。
- **代价/坑**：M6 也发现按**远程 IP 精确匹配**（`IP_REMOTE_ADDRESS`）在本机纯用户态该层**不命中**（AppID 条件却正常）——详见 `M6.md § 四`。所以"拦某进程全部 outbound（含 loopback）"用 AppID 形态很稳；"按具体远程 IP 精确拦"在纯用户态不可靠，要稳需内核态 callout（正是本节当年预判的"自己写 WFP callout driver"）。

### 坑 Y：企业机 EDR 客户端干扰

腾讯办公机实测组 X时，8.8.8.8:80 SYN 被 iOA 弹窗拦下（"hello_target.exe 正在尝试访问网络"）。**iOA 在比 Windows Firewall 更靠前的 hook 点**（WFP callout driver 或 LSP），对未知 exe 的公网出方向做进程级拦截。这**掩盖了 Windows Firewall 规则的直接可见效果**——但通过 `Get-NetFirewallApplicationFilter` 能证明规则确实按 Package SID 加进去且生效。

**教训**：企业级 EDR / SASE 主导的机器上测沙箱，需要区分"是我们的沙箱在拦" vs "是企业安全客户端在拦"。生产落地时两层可以互补。

### 生产级最佳实践 3 条

1. **broker 用管理员权限起** — `INetFwPolicy2.Add` 需要 `WRITE` firewall rule 权限；建议用服务或 schtask 拉起
2. **析构里 `RemoveRule`** — 避免防火墙规则表膨胀。Chromium sandbox 也这么做
3. **capability + allow 规则组合** — 想让 target 只连白名单主机时，先加一条 block-all，再加针对 remote address 或 port 的 allow 规则，都绑到同一 Package SID

### 面试话术 E：AppContainer 网络策略工程闭环

> "M2 加餐补丁我做了三层验证——第一层，`CreateAppContainerProfile` 只落地 Registry，不写防火墙规则，target 出方向完全通；第二层，broker 用 `INetFwPolicy2::Rules::Add` 加一条针对 Package SID 的 outbound TCP block 规则（QI 到 `INetFwRule3` + `put_LocalAppPackageId`），target 到公网被拦；第三层验证时踩到 loopback bypass 坑——Windows Firewall 对 127.0.0.1 默认不走规则匹配。**整条链走下来我明白了 Windows 沙箱的网络策略是三方合力**：AppContainer 提供主体（Package SID），Firewall 规则表提供策略，WFP 内核 callout driver 提供 loopback 之外的深度包检测和兜底——三者缺一不可。Chromium sandbox 用前两层；企业级 EDR（比如iOA）在第三层加自己的 hook。这也是 M4 我要做完整 WFP 白名单的动机——WFP callout driver 可以拦 Firewall 规则表拦不下来的路径（比如 loopback、raw socket）。"
