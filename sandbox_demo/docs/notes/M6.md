# M6 学习笔记 — WFP 用户态网络管控（按进程 / 按远程 IP 精确拦 outbound）

**面试口径**：M2 我用 Windows Firewall（防火墙规则）做过粗粒度网络管控，但它有两个硬伤——① 拦不住 loopback（127.0.0.1 回环流量绕过防火墙）；② 规则是"机器级/端口级"，很难精确绑定到"某一个进程 + 某一个远程 IP"。M6 换用更底层的 **WFP（Windows Filtering Platform）**，在 **ALE（应用层强制）** 分层上做**纯用户态 filter**，实现"只精确沙箱化 target 这一个进程的 outbound"，并**补上 M2 留的 loopback 债**。对应 JD：**网络沙箱 / 流量管控**。

---

## 一、WFP 是什么、和 Windows Firewall 什么关系

```
        应用 socket connect()
                │
                ▼
   ┌─────────────────────────────────────────┐
   │   BFE（Base Filtering Engine，基础过滤引擎）│  ← 用户态服务，管理所有 filter
   └─────────────────────────────────────────┘
                │  下发 filter 到内核
                ▼
   ┌─────────────────────────────────────────┐
   │   内核 filter engine：分很多"层(layer)"    │
   │   · ALE_AUTH_CONNECT_V4  (连接授权层)      │  ← 我们用这层拦 outbound
   │   · ALE_FLOW_ESTABLISHED_V4 (流建立层)     │
   │   · OUTBOUND_IPPACKET_V4 (IP 包层)         │
   │   · ...                                    │
   └─────────────────────────────────────────┘
```

- **Windows Firewall 本身就是 WFP 的一个"上层应用"**：防火墙规则最终也被翻译成 WFP filter 下发。我们直接用 WFP API（`fwpmu.h`）自己加 filter，比防火墙规则更底层、更精确。
- **WFP 相对防火墙的关键优势**：能挂在 `ALE_AUTH_CONNECT` 层，**loopback 连接也走这层** → 可拦 127.0.0.1（M2 的 Windows Firewall 拦不了）。

### 用户态 filter vs 内核态 callout
- **用户态 filter（本 M6 用）**：`FwpmFilterAdd0` 加一条"条件 → 动作(PERMIT/BLOCK)"规则，纯用户态、无需驱动。适合"按 AppID / 按 IP 精确 PERMIT/BLOCK"这类**判定型**管控。
- **内核态 callout**：注册 `FwpsCalloutRegister0` 回调，能看/改**每个包**内容（改包、DPI、按域名拦）。要写驱动，重。M6 不涉及。

## 二、DYNAMIC 会话：退出自动清理（省心的关键）

```cpp
FWPM_SESSION0 session{};
session.flags = FWPM_SESSION_FLAG_DYNAMIC;   // ⭐ 动态会话
FwpmEngineOpen0(nullptr, RPC_C_AUTHN_WINNT, nullptr, &session, &engine_);
```

- **DYNAMIC 会话**：本会话（这个引擎句柄）加的所有 filter/sublayer，在 `FwpmEngineClose0`（或进程退出）时**由 BFE 自动清理**，不留残留。
- 对照：非 DYNAMIC 会话的 filter 会**持久化**，必须手动 `FwpmFilterDeleteByKey0` 删，忘删就一直挂着污染全机网络。教学 demo 用 DYNAMIC 最省心。

### 自建 sublayer
所有 filter 挂在一个自有 GUID 的 sublayer 下（`FwpmSubLayerAdd0`），便于归组/隔离仲裁。sublayer 有自己的权重，决定不同 sublayer 之间的评估顺序。

## 三、两种形态（各一个 demo）

### 形态 C：按 AppID 精确拦 —— `m6_appid_demo.cc`【✅ 完全成功，M6 主力】

按 **exe 路径（AppId）** 精确拦 target 的**全部 outbound**：

```cpp
FWP_BYTE_BLOB* app_id = nullptr;
FwpmGetAppIdFromFileName0(app_path, &app_id);   // exe 路径 → 规范化设备路径 blob

FWPM_FILTER_CONDITION0 cond{};
cond.fieldKey = FWPM_CONDITION_ALE_APP_ID;
cond.matchType = FWP_MATCH_EQUAL;
cond.conditionValue.type = FWP_BYTE_BLOB_TYPE;
cond.conditionValue.byteBlob = app_id;

FWPM_FILTER0 f{};
f.layerKey = FWPM_LAYER_ALE_AUTH_CONNECT_V4;
f.action.type = FWP_ACTION_BLOCK;
f.numFilterConditions = 1;
f.filterCondition = &cond;
FwpmFilterAdd0(engine_, &f, nullptr, &id);
```

**实测效果（target 的 jailbreak-7 三行全 BLOCKED）**：
```
[7a] 8.8.8.8   : BLOCKED (WSAErr=10013)  ⭐
[7b] 1.1.1.1   : BLOCKED (WSAErr=10013)  ⭐
[7c] 127.0.0.1 : BLOCKED (WSAErr=10013)  ⭐ 连回环也拦——补上 M2 § 九留的 loopback 债！
```

- `WSAErr=10013`（`WSAEACCES`）= WFP 规则拒绝，是"被 WFP 拦下"的标准返回。
- **这是最贴近沙箱实战的形态**：不需要知道 target 要连哪些 IP，直接"这个进程整个禁网"。同机其他进程网络完全不受影响。

### 形态 A：按远程 IP 黑名单拦 —— `m6_demo.cc`【⚠️ 本机 IP 条件不命中，见 § 四】

对黑名单每个 IP 加一条 BLOCK（可叠加 AppID scope 限定到 target），其余默认放行：

```cpp
FWP_V4_ADDR_AND_MASK addr_mask{ntohl(ip), 0xFFFFFFFF};  // addr+/32 掩码，主机序
FWPM_FILTER_CONDITION0 conds[2]{};
conds[0].fieldKey = FWPM_CONDITION_IP_REMOTE_ADDRESS;
conds[0].matchType = FWP_MATCH_EQUAL;
conds[0].conditionValue.type = FWP_V4_ADDR_MASK;
conds[0].conditionValue.v4AddrMask = &addr_mask;
// conds[1] = 可选 AppID scope
```

**为什么黑名单而非白名单**：白名单（默认拦 + 白名单 PERMIT 放行）需要 PERMIT 确定性压过兜底 BLOCK，涉及 `CLEAR_ACTION_RIGHT` / 独立 sublayer 权重等 WFP 仲裁深水区（实测 PERMIT 压不住兜底 BLOCK）。黑名单只有 BLOCK，命中即拦、不命中即放行，行为确定。

## 四、⭐ IP 精确匹配踩坑全记录（本 milestone 最硬的坑）

**现象**：形态 A 里 `IP_REMOTE_ADDRESS` 条件的 filter **装配完全正确**（netsh 可见 `8.8.8.8/32`），但 target 连 8.8.8.8 **就是不被拦**（`WSAErr=0`，SYN 正常出去）。而**同层同会话的 AppID 条件（形态 C）却完全正常**。

### 4.1 排查过程（逐一证伪，全部有实测）

| # | 假设 | 验证手段 | 结果 |
|---|---|---|---|
| 1 | 字节序错 | UINT32/ADDR_MASK × 主机序(`ntohl`)/网络序 **四种组合** | ❌ 全部装上不命中 |
| 2 | filter 没装上 | `netsh wfp show filters` dump | filter 100% 正确：层对、`FWP_MATCH_EQUAL`、`FWP_V4_ADDR_MASK`、`8.8.8.8/32`、`FWP_ACTION_BLOCK` |
| 3 | AppID scope 把 AND 卡死 | `M6_NO_SCOPE=1` 去 scope 只留纯 IP | ❌ 纯 IP 单条件也不命中 |
| 4 | 有高权重 PERMIT-all 短路 | dump ALE_AUTH_CONNECT_V4 全层 filter | 无无条件 PERMIT-all，排除 |
| 5 | 换层能救 | 换 `ALE_FLOW_ESTABLISHED_V4` | ❌ 仍不拦（且该层裸 BLOCK 需 callout 才生效） |
| 6 | **BLOCK 本身失效？** | **`M6_BLOCK_ALL=1` 去掉 IP 条件、无条件 BLOCK** | ✅ **三行全拦 10013！** |

### 4.2 终极对照实验（第 6 行）= 决定性证据

`M6_BLOCK_ALL=1`（同一条 filter，唯一区别是**去掉 IP 条件**）→ **8.8.8.8/1.1.1.1/127.0.0.1 三行全 BLOCKED**。

这一步把问题**精确锁死**：
- ✅ 本会话/sublayer 的**裸 BLOCK 在 ALE_AUTH_CONNECT_V4 层完全有效**
- ✅ AppID 条件正常
- ❌ **唯独 `IP_REMOTE_ADDRESS` 条件求值不命中**

### 4.3 结论（根因）

**在本机，纯用户态 DYNAMIC filter + `ALE_AUTH_CONNECT_V4` 层，按 `FWPM_CONDITION_IP_REMOTE_ADDRESS` 精确匹配对 target 的 outbound `connect()` 不命中**——尽管 filter 装配无懈可击、`netevents` 审计也零 drop 记录。这属于 **WFP 分层语义 + 本机环境（BFE 仲裁 / 安全软件 filter 布局）层面**的问题：`connect()` 授权瞬间该 filter 的远程 IP 求值被短路。**纯用户态代码改不动。**

> 要真正稳定按远程 IP 拦，需内核态 callout（在流建立时按 remote IP 分类阻断），或把 sublayer 权重提升到系统级——超出本教学 demo 范围。

### 4.4 附带踩到的两个工程坑（同样重要）

1. **`netsh` 显示 ≠ 运行时匹配**：`netsh` 按主机序反解 IP 显示，"显示对"不代表内核运行时按同一字节序比对。排字节序问题不能只信 netsh 显示。
2. **exe 时间戳静默未更新的编译陷阱**：改完代码"编译成功"，但如果 exe 被上一次残留进程占用，链接会 `LNK1168` 失败——而失败信息可能被 PowerShell CLIXML 噪声掩盖，你以为编译好了、实际跑的还是旧 exe（本 milestone 因此白跑一轮 `FWP_V4_ADDR_MASK` 旧版复现 WRONG_SESSION）。**硬规矩：改完必"杀进程 → 删 exe → 编译 → 确认 exe 时间戳更新"三步走。**

## 六、面试三连问

1. **WFP 和 Windows Firewall 什么关系？** —— Firewall 是 WFP 的上层应用，防火墙规则最终翻译成 WFP filter。直接用 WFP API 更底层、能拦 loopback、能精确绑进程。
2. **DYNAMIC 会话解决什么？** —— filter 随进程退出由 BFE 自动清理，不留残留污染全机网络；非 DYNAMIC 要手动删。
3. **按 AppID 拦和按 IP 拦哪个稳、为什么？** —— AppID 稳（connect 瞬间进程路径就已知，条件必命中）；按远程 IP 在纯用户态 ALE_AUTH_CONNECT 层可能因分层语义/环境仲裁不命中，要稳需内核态 callout。（本 milestone 的实测硬结论）
