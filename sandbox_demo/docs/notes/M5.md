# M5 学习笔记 — 反注入 + 运行时检测（防御双层：内核挡 + 用户态查）

**面试口径**：M4 我做"攻"——broker 主动注入 target、在里面 inline hook。M5 是它的**镜像面**：怎么让"别人别想注入我 / 篡改我"。M5 的关键洞见是——**反注入不是一层，是两层配合**：① **内核级护栏（Process Mitigation Policy）**：从娘胎带出来、无法绕过，第一道也是最强一道，M1 其实就装过（只是 M4 为了能注入把它关了）；② **用户态运行时自检**：内核挡不住 / 开不满时，进程自己主动"查有没有被注入、关键 API 有没有被 hook"，是补位的第二道防线。生产级沙箱（Chromium / EDR）都是这两层配合。M5 把这两层都做出来，并用 **M4 的 injector 当真实攻击者**做攻防对照验证。

对应 JD：**W4 —— DLL 注入 / API Hook / 反注入**（这一篇是"反注入"的正面）。

---

## 一、M5 的双层防御模型

```
                        有人想往 target 注入 DLL / inline hook
                                     │
          ┌──────────────────────────┴──────────────────────────┐
          ▼                                                       ▼
   第一层：内核级护栏（Mitigation Policy）              第二层：用户态运行时自检
   —— 从进程创建就绑在 EPROCESS 上，无法绕过            —— target 自己"查自己"
   ┌────────────────────────────────────┐            ┌────────────────────────────────┐
   │ PROHIBIT_DYNAMIC_CODE               │            │ ① LdrRegisterDllNotification    │
   │   拦 inline hook 改可执行内存        │            │    抓 DLL 加载事件（白名单外告警）│
   │ BLOCK_NON_MICROSOFT_BINARIES        │            │ ② 扫可疑远程线程                 │
   │   拦加载未签名的注入 dll ⭐主力       │            │    （起点=LoadLibraryW/裸内存）  │
   │ DISABLE_EXTENSION_POINTS            │            │ ③ 关键 API inline-hook 头字节自检 │
   │   拦 AppInit_DLLs/全局钩子式注入      │            │                                  │
   └────────────────────────────────────┘            └────────────────────────────────┘
          │                                                       │
   注入根本进不来（拦）                                    注入进来了也能发现（报）
```

**为什么两层都要**：
- 内核层是"**拦**"不是"**报**"——被拦下的攻击尝试，target 不一定知道发生过；安全产品需要"感知到有人在打我"（告警/取证/熔断）。
- 兼容性：不是所有环境都能开满 mitigation（target 可能依赖某个未签名第三方 DLL，就不能开 BLOCK_NON_MICROSOFT_BINARIES）。开不满时，用户态检测补位。

## 二、第一层：反注入 Mitigation（broker 侧，m5_demo.cc）

M5 broker 与 M4 的**唯一核心区别**：M4 关掉反注入三件套让注入得手，M5 **开满**：

```cpp
// m5_demo.cc BuildMitigation（defense_off=false 主场景）
c.prohibit_dynamic_code    = true;  // 禁改可执行内存 → 拦 inline hook 改 API 头字节
c.strict_signed_dll        = true;  // 只许微软签名 DLL → 拦加载未签名注入 dll（主力）
c.disable_extension_points = true;  // 禁 AppInit/全局钩子 → 拦老式 SetWindowsHookEx 注入
```

这三个 policy 位在 M1 的 `MitigationConfig` 里早就有——**M5 不是新造轮子，是把 M1 的护栏正面用在"反注入"语义上**。它们由 `STARTUPINFOEX + PROC_THREAD_ATTRIBUTE_MITIGATION_POLICY` 在**进程创建时**绑到 EPROCESS，加载器 / 内存分配器 / 映像校验器直接按策略工作，用户态无法绕过。

### 三个位分别防哪种注入手法

| Mitigation 位 | 防的注入手法 | 拦截点 |
|---|---|---|
| `BLOCK_NON_MICROSOFT_BINARIES` | 远程线程 LoadLibrary 注入未签名 dll（M4 那种） | 内核映像校验：LoadLibraryW 加载时对 dll 做 Authenticode 校验，未签名一律拒 |
| `PROHIBIT_DYNAMIC_CODE` | inline hook 改 API 机器码 / 写 shellcode 到 RWX 内存 | 内存管理器：禁止把内存页改成可执行、禁改现有可执行页 |
| `DISABLE_EXTENSION_POINTS` | AppInit_DLLs / SetWindowsHookEx 全局钩子 / IME 注入 | 加载器：忽略这些"扩展点"式的自动加载 |

## 三、第二层：用户态运行时自检（core/self_defense.{h,cc}）

跑在**被保护进程（target）自己内部**——这是它和 M0~M4 的根本区别：前面都是 broker 从外部配置 target，M5 的检测天然是"我自己查我自己"。三个手段：

### 手段①：DLL 加载通知（LdrRegisterDllNotification）
```cpp
// ntdll 半公开 API，GetProcAddress 动态取
LdrRegisterDllNotification(0, &DllNotificationCallback, nullptr, &cookie);
```
注册一个回调，进程**每次 LoadLibrary / 映射映像**时内核加载器都会回调我们，带上被加载模块全路径。对照白名单（System32/WinSxS 等可信路径），**白名单外的 DLL 被加载即告警**——正好抓 M4 那种 `LoadLibraryW(sandbox_hook.dll)` 注入。比轮询遍历模块列表实时得多：加载瞬间就知道。

### 手段②：可疑远程线程扫描
```cpp
CreateToolhelp32Snapshot(TH32CS_SNAPTHREAD) → 枚举本进程线程
NtQueryInformationThread(ThreadQuerySetWin32StartAddress) → 取每个线程起始地址
```
判据（启发式）：
- 起点**正好是 `LoadLibraryW`/`LoadLibraryA`** → 典型远程线程注入入口（M4 CreateRemoteThread 的特征）
- 起点**不落在任何已加载模块内** → 疑似 VirtualAllocEx 出来的裸内存 shellcode

### 手段③：关键 API inline-hook 篡改自检
```cpp
BYTE* fn = GetProcAddress(kernel32, "CreateFileW");
// 读头字节，看是否被改成跳转（inline hook 特征）：
//   E9 xx xx xx xx      → jmp rel32
//   FF 25 ...           → jmp [rip+disp]
//   48 B8 ... + FF E0   → mov rax,imm64 + jmp rax
//   68 ...              → push+ret
```
正常 CreateFileW 开头不会是跳转指令；被 M4 那种 inline hook 改过就会。这是"反篡改 / 完整性自检"的最小实现——**直接对应 M4 appendix §一.5 讲的"头字节改成 jmp"**。

## 四、实测：攻防三组对照（都是硬证据）

M5 用 **M4 的 injector 当真实攻击者**，三组对照（`run_m5*.bat`）：

| 脚本 | 防御 | 攻击 | 预期 | 实测 |
|---|---|---|---|---|
| `run_m5.bat` | 全开 | 无 | 自检干净（基线） | 干净 ✅（附赠 iOA 注入被挡彩蛋） |
| `run_m5_attack.bat` ⭐ | 全开 | 有 | 注入被内核挡 + 自检干净 | **注入被挡（0xC0000428 弹窗）** ✅ |
| `run_m5_defenseoff.bat` | 关闭 | 有 | 注入得手（复现 M4）+ 自检报警 | **注入得手 + 自检报警 3 条** ✅ |

### 证据 1：内核层防御——同一 injector 开/关防御结果相反

用 `(Get-Process hello_target).Modules` 查 target 有没有被注入 sandbox_hook.dll——同一套 injector：

```
[防御ON+攻击]  sandbox_hook 注入进 target?  False   ← ⭐ 反注入 mitigation 挡住了
[防御OFF+攻击] sandbox_hook 注入进 target?  True    ← 关掉防御，注入得手（复现 M4）
```

**同一套 M4 injector，开防御注入不进去（False），关防御就得手（True）**——直接证明反注入 mitigation 生效。

### 证据 2：注入被挡的**精确位置**——LoadLibraryW 加载环节，不是内存操作

`run_m5_attack.bat`（防御全开 + 攻击）时 broker 日志 + 弹窗揭示了更精确的真相：

```
[+] 反注入护栏: prohibit_dynamic_code=1 strict_signed_dll=1 disable_extension_points=1
[+] 【攻击】用 injector 尝试注入 ...\sandbox_hook.dll ……
[+] Injector: 远程线程已起 tid=42728 入口=LoadLibraryW 路径=...\sandbox_hook.dll   ← 远程线程起来了！
        ↓
弹窗: hello_target.exe - 损坏的映像
     ...\sandbox_hook.dll ... 错误状态 0xc0000428                                ← 挡在这一刻
```

**注入四件套里前三步（VirtualAllocEx / WriteProcessMemory / CreateRemoteThread）全部成功**——远程线程 `tid=42728` 确实在 target 里跑起来了。真正被挡的是**第四步远程线程执行 `LoadLibraryW(sandbox_hook.dll)` 加载未签名 dll 的那一刻**，被内核映像校验拒绝，报 `0xC0000428 (STATUS_INVALID_IMAGE_HASH)`。

> ⭐ 精确认知：**反注入 mitigation（BLOCK_NON_MICROSOFT_BINARIES）不是阻止"注入动作"，而是阻止"未签名代码被映射进地址空间"**——它拦的是最后的加载环节，前面的内存操作/起线程它管不着（那些是标准进程 API）。这比"注入被挡"笼统说法更准确。

### 证据 3：用户态检测层——注入得手后自检报警（DebugView / 控制台）

`run_m5_defenseoff.bat`（关防御 + 攻击）注入得手，target 自检报出 3 条告警：

```
[selfcheck][ALERT][可疑DLL]   白名单外 DLL 被加载: ...unsigned_probe.dll
[selfcheck][ALERT][API被篡改]  kernel32!CreateFileW 头字节被改 (E9 jmp rel32) —— 疑似被 inline hook
[selfcheck][ALERT][API被篡改]  kernel32!CreateFileA 头字节被改 (FF25 jmp [rip+disp]) —— 疑似被 inline hook
```

**内核没挡住时，用户态检测层兜底发现了。** 且有两个超出预期的收获：

- **手段③抓到了两个不同来源的 hook**：`CreateFileW` 的 `E9 jmp rel32` 是**我自己的 sandbox_hook.dll（MinHook）**钩的；`CreateFileA` 的 `FF25 jmp [rip+disp]` **不是我钩的**（我只钩 W），是机器上的**真实 EDR（腾讯 iOA）**钩的。**说明手段③对任意来源的 inline hook 都有效**，不挑攻击方。
- **可疑 DLL 报的是 unsigned_probe.dll**：那是 jailbreak-4 加载的探测 dll（防御关了所以加载成功）。sandbox_hook.dll 没单独列出，是因为它在 DLL 监控注册**之前**（resume 前）就注入了；但它的存在被手段③（CreateFileW=E9）精确抓到，两条线互补。

### 证据 4（实战彩蛋）：真实 EDR 的注入也被挡——两个 0xC0000428

M5 意外收获了 `0xC0000428` 弹窗，而且 `run_m5_attack.bat` 一次跑出**三次**弹窗——恰好对应**三种不同来源**想往 target 加载非微软签名 dll，全被同一个 `BLOCK_NON_MICROSOFT_BINARIES` 无差别拦下：

| # | 被拦 dll | 谁想加载它进 target | 来源类型 |
|---|---|---|---|
| 1 | `sandbox_hook.dll` | **我的 m5_demo `--attack`**（injector 远程线程 LoadLibraryW） | 外部攻击者**主动注入**（跨进程 CreateRemoteThread） |
| 2 | `iOA\...\TxUmon64.dll` | **腾讯 iOA 安全软件**（真实 EDR 自动注入所有进程） | **第三方软件注入**（系统级自动） |
| 3 | `unsigned_probe.dll` | **target 自己**（jailbreak-4 主动 LoadLibraryW） | target **进程内自加载** |

三个 dll 来自三个完全不同的加载方，全非微软签名，全报 `0xC0000428 (STATUS_INVALID_IMAGE_HASH)`。

**两个关键结论**：
1. **`run_m5_attack.bat` 比 `run_m5.bat` 正好多第 1 次弹窗（sandbox_hook.dll）**——因为唯一变量就是多了 `--attack`（我自己发起的那次注入）。控制变量法在弹窗上的直接印证：多一个 `--attack`，多一次注入尝试，多一次被拦弹窗。
2. **`BLOCK_NON_MICROSOFT_BINARIES` 对三种来源一视同仁**——因为它的拦截点是**内核映像映射校验**：不管是外部注入、EDR 注入、还是 target 自己 LoadLibrary，最终都要走"内核把 dll 映射进地址空间"这一步，签名不过就拒。**它连 target 自己想加载非签名 dll 都拦**（unsigned_probe 就是证明），比"只防外部注入"强得多。

这也解释了为什么 Chromium renderer 开这个 mitigation 会和某些杀软冲突、需要兼容名单——真实世界里想往你进程塞 dll 的"善意方"（EDR/输入法/录屏软件）非常多。

> 附：有无弹窗本身就是防御开关的指示灯——防御开（strict_signed_dll=1）→ 未签名 dll 加载触发 0xC0000428 弹窗；防御关 → 都能加载，无弹窗。三组实测正好印证。

## 五、金牌面试话术

### 话术 A：反注入是两层，不是一层
> "反注入我做了两层。第一层是内核级 mitigation——PROHIBIT_DYNAMIC_CODE 拦 inline hook 改可执行内存，BLOCK_NON_MICROSOFT_BINARIES 拦加载未签名 dll，DISABLE_EXTENSION_POINTS 拦 AppInit/全局钩子式注入。它从进程创建就绑在 EPROCESS 上、无法绕过，是最强一道。但它只'拦'不'报'，而且兼容性上不一定能开满。所以第二层是用户态运行时自检——进程自己用 LdrRegisterDllNotification 抓 DLL 加载、扫可疑远程线程、校验关键 API 头字节有没有被改成 jmp。两层配合：内核挡得住的挡，挡不住/开不满的靠用户态检测兜底报警。这也是 Chromium 和主流 EDR 的思路。"

### 话术 B：我用同一套注入器做了攻防对照
> "M5 我没有另写一个'假攻击'，而是直接拿 M4 真实的远程线程注入器当攻击方。开满反注入 mitigation 后再跑它——注入失败，target 模块列表里查不到我的 hook dll（False）；把防御关掉，同一套注入器立刻得手（True）。这个 A/B 对照是最硬的证据：不是我说防御有效，是同一个攻击在有无防御下结果相反。挡住它的具体是 BLOCK_NON_MICROSOFT_BINARIES——我的 hook dll 没有微软签名，远程 LoadLibraryW 时内核 Authenticode 校验直接拒。"

### 话术 C：inline-hook 自检的原理（呼应 M4）
> "用户态检测里有一条是校验关键 API 完整性。原理很直接——inline hook 会把目标函数（比如 CreateFileW）开头几字节改成一条 jmp 跳到钩子。所以我读 CreateFileW 的头字节，看它是不是 E9(jmp rel32) / FF25(jmp [rip+disp]) / 48B8+FFE0(mov rax,imm64+jmp rax) 这些跳转形态。正常函数开头不会是这些。被我 M4 那套 MinHook 钩过的，头字节就是 E9——自检立刻能报出来。这其实是 M4 和 M5 的闭环：M4 我改头字节做 hook，M5 我读头字节查 hook。"

### 话术 D：为什么 M4 要关掉这些 mitigation（攻防同源）
> "有意思的是，M4 为了能把 hook 注进去，我特意关掉了 PROHIBIT_DYNAMIC_CODE 和 BLOCK_NON_MICROSOFT_BINARIES——因为它们会拦住我自己的注入。这恰恰说明这两个 mitigation 本质就是'内核级反注入'。所以 M5 的第一层根本不用新造，就是把 M4 关掉的那两个正面开回来。攻和防用的是同一套机制的两面——你理解了怎么绕过一个防御，就理解了这个防御在防什么。"

### 话术 E：LdrRegisterDllNotification vs 轮询
> "检测'有没有被注入 DLL'，最朴素的做法是定时遍历模块列表（Toolhelp 快照）比对。但那是轮询，有窗口期——注入后到下次扫描之间发现不了。我用的是 LdrRegisterDllNotification，ntdll 的半公开 API，注册后每次有模块被映射进来内核加载器都会实时回调，带模块全路径。加载瞬间就能对照白名单告警，没有窗口期。这是比轮询更专业的做法，很多 EDR 用它。"

### 话术 F：实战彩蛋——真实 EDR 的注入也被挡 + 自检抓到两个来源的 hook
> "我在装了腾讯 iOA 的机器上跑，收获两个意外证据。第一，开 BLOCK_NON_MICROSOFT_BINARIES 后，连 iOA 想往我 target 注入它的 DataProtection 监控 DLL 都被内核挡下了，报 0xC0000428 签名校验失败——和我自己的 hook dll 被挡是同一个错误码。这说明这个 mitigation 无差别拦所有非微软签名 dll，包括善意的安全软件，这也是它会和杀软冲突、需要兼容名单的原因。第二，关掉防御让注入得手后，我的 API 完整性自检同时报出两条：CreateFileW 被改成 E9 近跳——那是我自己的 MinHook 钩的；CreateFileA 被改成 FF25 间接跳——那不是我钩的，是 iOA 钩的。**我的自检对任意来源的 inline hook 都有效，不挑攻击方**。而且我发现注入被挡的精确位置不是'起远程线程'那步——远程线程其实成功起来了——而是远程线程执行 LoadLibraryW 加载未签名 dll 的那一刻被内核映像校验拒。所以这个 mitigation 拦的是'未签名代码被映射进地址空间'，不是'注入动作'本身。"

## 六、这轮踩的坑

### 坑：MinHook vendored 源码丢失导致全工程 configure 失败
`src/third_party/minhook` 是 clone 进来的**未跟踪目录**，某次 git 操作（疑似 git clean）把它清掉了。CMake 的 minhook 库找不到 buffer.c，`add_library` 报 "No SOURCES given to target: minhook"，整个 configure 挂掉——连不依赖 minhook 的 M5 代码也编不了。修法：重新 clone MinHook + 在 .gitignore 里保留它避免再被清。**教训：vendored 第三方源码要么纳入版本控制，要么在 .gitignore 明确 !例外保护，不能放任为未跟踪状态。**

### 坑：LNK1168 exe 被占用
残留的 target 心跳进程锁住 hello_target.exe，link 写不进去。这是 demo 型工程的通病（target 是死循环心跳），编译前先杀掉残留进程即可。
