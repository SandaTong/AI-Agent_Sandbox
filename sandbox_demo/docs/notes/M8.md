# M8 学习笔记 — 用户态文件 Broker（文件访问从"降权"升到"代理 + 策略引擎"）

> **一句话**：给"什么都不让 target 碰"的沙箱补上**受控的文件访问出口**——敏感文件操作由沙箱外的 broker 按策略代劳，不再一刀切全禁。
>
> **M8 做了什么**：在 M3 的命名管道 IPC 骨架上，做了两条互补的文件管控路线——
> - **形态 A（主，IPC 文件 Broker）**：把 M3 那个"单目录只读"的最小 broker 升级成生产级策略引擎：① 多规则白名单（只读目录 / 可写目录分离）② 读/写/创建多操作（协议加 access/disposition，向后兼容 M3）③ **防 TOCTOU**——先开句柄再用 `GetFinalPathNameByHandle` 拿"事后真身"校验白名单（解 symlink/短名/大小写）④ **最小权限句柄回传**——DuplicateHandle 按本次策略允许的最小权限复制。
> - **形态 B（辅，DENY-ACE）**：不改 IPC，broker 起 target 前直接给敏感目录的 NTFS DACL 追加一条针对 target 的 **DENY-WRITE ACE**，让 target 自己 `CreateFileW(写)` 被内核一票否决。
>
> **达到的目的**：证明沙箱里"文件访问"这一维度既能用**主动授予**（broker 发句柄，Chromium sandbox 套路，细粒度）也能用**被动剥夺**（改客体 ACL 从外部收权，目录级），两者纵深互补。实测：形态 A 四点增强全绿（读放行 / 越权真身拒绝 / 写创建 / 只读目录写拒绝），形态 B jailbreak-9 从 gle=3 变 gle=5（DENY-ACE 挡下）。

**面试口径**：M0~M2 把 target 关进笼子（Job / restricted token / Low IL / AppContainer），笼子越严 target 越什么都读不了写不了。真实 agent 要读工程目录、要把结果写到 `outputs/`——这些**敏感文件操作必须委托沙箱外的 broker 代劳**。M3 我搭了 Broker/Target 命名管道 IPC 骨架，做了"broker 代劳只读打开单目录白名单文件 + DuplicateHandle 回传"的最小版。**M8 把这个文件 broker 升级成生产级**：多规则白名单（读写分离）、读/写/创建多操作、**防 TOCTOU 的事后真身校验**、**最小权限句柄回传**；并另开一个 demo 演示与 IPC 代劳互补的另一条路线——**直接改客体 NTFS DACL、用 DENY-ACE 从外部剥夺 target 的写权限**。对应 JD：**沙箱文件访问代理 / 权限收敛 / 安全边界设计**。

## 一、M8 在整套沙箱里的位置

```
target（沙箱内，几乎无权限）
   │  "帮我打开/写 C:\...\file"   ← IPC 请求（形态 A）
   ▼
broker（沙箱外，有权限）
   ① 收请求 ② 策略引擎判定（路径白名单 + 读写维度）
   ③ 先开句柄，用真身校验（防 TOCTOU） ④ 按最小权限 DuplicateHandle 回传
   ▼
target 拿到"恰好够用"的句柄继续干活

另一条互补路线（形态 B）：
broker 起 target 前，给敏感目录 DACL 追加 DENY-WRITE ACE
   ▼
target 自己 CreateFileW(写) → 内核 DACL 检查 DENY 优先命中 → ACCESS_DENIED
```

**两条路线的哲学差异**（面试高频对比）：

| | 形态 A：IPC 文件 Broker | 形态 B：DENY-ACE |
|---|---|---|
| 思路 | 主动授予：默认全禁，broker 按策略"发"句柄 | 被动剥夺：改客体 ACL 从外部收权 |
| 改谁 | 不改文件；改的是"谁替 target 打开" | 直接改文件/目录的 DACL |
| 粒度 | 极细（每次请求逐条策略判定 + 最小权限句柄） | 目录级（一条 ACE 覆盖整个子树） |
| target 感知 | 需改造 target 走 IPC | target 无需改造，照常 CreateFileW |
| 典型用途 | renderer 请 broker 读工程文件 | 快速把某目录对某进程"只读化" |
| 工业参照 | Chromium sandbox broker | AppContainer / 最小 ACL |

## 二、形态 A：文件 Broker 策略引擎相比 M3 的四点增强

M3 的 broker 只有：单目录前缀白名单 + `..` 拒绝 + 只读打开 + `DUPLICATE_SAME_ACCESS`。M8 补齐了生产上真正要做的四件事：

### 2.1 多规则白名单（读写分离）

M3 是"一个只读目录"。M8 是一组 `FilePolicyRule { dir_prefix, allow_write }`：

```
C:\sandbox_share\   allow_write=false   ← 只读目录
C:\sandbox_write\   allow_write=true    ← 可写目录
```

判定分两级：**先命中某条目录规则**，**再看该规则是否允许本次 access**。对只读目录请求写 → `kAccessNotAllowed`（和"路径根本不在白名单"的 `kDenied` 区分开，观测更细）。

### 2.2 读/写/创建多操作（协议扩展 + 向后兼容）

`OpenFileRequest` 从 M3 的 4 字节（只有 `path_chars`）扩展到 12 字节，追加 `access_mode` / `disposition`：

- `AccessMode`：`kRead` / `kReadWrite` / `kWrite` —— **只认这三种枚举，绝不透传 target 传来的裸 Win32 权限位**（防 `WRITE_DAC` / `WRITE_OWNER` / `GENERIC_ALL` 去改 ACL）。broker 内部翻译成收敛过的 `dwDesiredAccess`。
- `Disposition`：`kOpenExisting` / `kOpenAlways` / `kCreateAlways` → `CreateFileW` 的 disposition。

**向后兼容**：协议 version 提到 2，但 `ValidateHeader` 同时放行 v1(M3)/v2(M8)。broker 按 body 实际长度自适应：只有 4 字节 → 老 v1 请求，按"只读 + OpenExisting"处理；12 字节 → 读 access/dispo。老布局是新布局的前缀（wire-compatible）。

### 2.3 防 TOCTOU：先开句柄，再用真身校验 ⭐（最硬的一点）

M3 是"先对字符串路径判白名单，再 CreateFileW"。这有 **TOCTOU（Time-Of-Check to Time-Of-Use）** 漏洞：字符串和真正打开的文件对象之间存在检查时机差，symlink / 目录联结(junction) / 8.3 短名 / ADS(`::$DATA`) / 相对分量 都能让"看起来在白名单里的字符串"实际指向白名单外的文件；攻击者还能在校验通过后、打开前把路径换掉。

M8 做法：

```
① 先用请求的 access 以 OPEN_EXISTING 打开句柄（拿到内核文件对象）
② GetFinalPathNameByHandleW 让内核回吐这个句柄【真正指向】的规范全路径
   （已解析 symlink/junction/短名，统一磁盘真实大小写，去掉 \\?\ 前缀）
③ 用这个"事后真身"去比白名单
④ 通过后再按真实 disposition 正式打开
```

关键：**校验对象和最终使用对象是同一个内核文件对象**，杜绝检查时机攻击。创建类请求（文件还不存在）退化为"对父目录开句柄拿父目录真身"再拼文件名校验，避免"先创建了白名单外文件再拒绝"的副作用。

### 2.4 最小权限句柄回传

M3 用 `DuplicateHandle(..., DUPLICATE_SAME_ACCESS)` 原样复制，broker 句柄带什么权限 target 就拿什么。M8 显式指定 `dwDesiredAccess` = 本次策略允许的最小权限（只读请求只给 `GENERIC_READ`，写请求给 `GENERIC_READ|GENERIC_WRITE`），把多余权限位裁掉。即使 target 被攻破，拿到的句柄也放大不了权限。

**对应 target 现象**（jailbreak IPC 演示，`m8_demo` 下）：
```
[ipc] 打开 C:\sandbox_share\hello.txt        -> OK（读到内容）
[ipc] 打开 ...\drivers\etc\hosts             -> BLOCKED（越权路径 kDenied）
[ipc] 写 C:\sandbox_write\agent_out.txt      -> OK（broker 代劳落盘）⭐
[ipc] 写 C:\sandbox_share\should_fail.txt    -> BLOCKED（命中只读规则 kAccessNotAllowed）⭐
```

## 三、形态 B：DENY-ACE 从外部剥夺写权限

### 3.1 原理：为什么 DENY-ACE 一定赢 ALLOW

Windows 访问检查按 ACE 在 DACL 里的顺序逐条评估，**DENY 类型只要命中所需权限位就立即拒绝**，不再看后面的 ALLOW。规范的 canonical ACE 顺序就是 DENY 在前、ALLOW 在后。所以哪怕目标目录本来有 `Users:(M)` 的写 ALLOW，追加一条针对 target 主体 SID 的 DENY-WRITE，也会一票否决。

### 3.2 落地：`core/file_acl.{h,cc}`

```
GetNamedSecurityInfoW  读现有 DACL
   ▼
EXPLICIT_ACCESSW { grfAccessMode = DENY_ACCESS,
                   grfAccessPermissions = FILE_GENERIC_WRITE|WRITE_DATA|APPEND_DATA|DELETE...,
                   grfInheritance = CONTAINER_INHERIT_ACE|OBJECT_INHERIT_ACE }  ← 目录+文件继承
   ▼
SetEntriesInAclW  合并（DENY 自动排到 ALLOW 前）
   ▼
SetNamedSecurityInfoW  写回目录 DACL
```

两个要点：
1. **目标 SID 用"当前进程用户 SID"**。因为 M0 的 restricted token 从当前进程 token 派生，**用户 SID 不变**（restricted 只移除 privilege / 加 restricting SID），所以对当前用户 SID 下 DENY 就能作用到 target。
2. **必须带继承标志**（`CONTAINER_INHERIT_ACE|OBJECT_INHERIT_ACE`），才能覆盖目录下**新建的文件**（jailbreak-9 写的是目录里的文件）。
3. **最小侵入 + 可回滚**：只追加一条 DENY ACE，`FileAcl` 析构或 `RemoveDenyWrite()` 用 `REVOKE_ACCESS` 删回去，不污染真实目录权限。demo 目录用临时的 `C:\sandbox_protected`。

**对应 target 现象**（jailbreak-9，`m8_denyacl_demo` 下）：
```
[jailbreak-9] 直接写受保护目录 : BLOCKED (gle=5 ACCESS_DENIED，DENY-ACE 生效) ⭐
（不加 DENY-ACE 时同一行是 SUCCESS）
```

## 四点五、实测输出存档（2026-08-18 亲跑，全绿）

### 形态 A（run_m8.bat）— IPC 文件 Broker 四点增强全部坐实

| 观察点 | broker 侧日志 | target 侧结果 | 验证的增强点 |
|---|---|---|---|
| 只读目录**读** | `已代劳打开(真身校验通过) C:\SANDBOX_SHARE\HELLO.TXT` | `打开 hello.txt -> OK，读到 30 字节` | 白名单命中放行 |
| 越权路径**读** | `拒绝越权路径(真身): C:\WINDOWS\SYSTEM32\DRIVERS\ETC\HOSTS` | `BLOCKED（越权路径）` | **GetFinalPathNameByHandle 真身校验**（broker 能开 hosts，但真身不在白名单→kDenied） |
| 可写目录**写/创建** | `OpenFile 请求 ... access=1 dispo=2` → `已代劳打开 C:\SANDBOX_WRITE\AGENT_OUT.TXT` | `写 -> OK，写入 38 字节` | 读写分离 + 多操作（v2 协议 access=1/dispo=2） |
| 只读目录**写** | `命中只读规则但请求写，拒绝: C:\SANDBOX_SHARE\SHOULD_FAIL.TXT` | `BLOCKED（命中只读规则）⭐` | 两级判定（kAccessNotAllowed ≠ kDenied） |

落盘验证：`C:\sandbox_write\agent_out.txt` 生成，38 字节 = `written-by-broker-on-behalf-of-target\n`。
`access=1 dispo=2` 坐实走的是 M8 v2 请求（12 字节 body），协议向后兼容扩展成功。

### 形态 B（run_m8_denyacl.bat）— DENY-ACE 的 gle 3→5 对照

broker 侧完整加锁+自动回滚闭环：
```
FileAcl: 已给 C:\sandbox_protected 追加 DENY-WRITE(继承) for SID S-1-5-21-...-1251219
...（target 起来跑越狱测试）...
Target 退出，exit_code=0x0
FileAcl: 已移除 C:\sandbox_protected 上的 DENY-WRITE      ← 析构自动回滚
```

target 侧 jailbreak-9 的**关键对照**：
- Demo 1（m8_demo，没建目录也没加 ACE）：`gle=3`（PATH_NOT_FOUND）
- Demo 2（m8_denyacl_demo，加了 DENY-ACE）：`gle=5`（ACCESS_DENIED，DENY-ACE 生效）⭐

**gle 从 3 变 5 就是形态 B 的核心证据**：目录存在了，但写被内核 DACL 检查的 DENY ACE 一票否决。

### ⚠️ 一个真实副作用（面试可当加分点讲）

加了 DENY-WRITE(含继承) 后，**当前用户用资源管理器双击进该目录会被弹"你当前无权访问该文件夹"**。原因：DENY ACE 里带了 `FILE_WRITE_ATTRIBUTES` 等位 + 目录继承，explorer 进目录时的若干带写意图探测命中 DENY，Windows 对"命中任何 DENY 就整体保守"→ 弹权限提示。点"继续"会让 explorer **用管理员往 DACL 追加一条 Everyone ALLOW**（这跟我们的 REVOKE 回滚是两码事，会污染目录 ACL）。

**教训**：① DENY ACE 的权限位要按需最小化，写场景别顺手带 explorer 也要用的位；② 测试目录建议用临时目录，跑完 `rmdir /s C:\sandbox_protected` 重建最干净；③ 想确认 ACL 干净用 `icacls C:\sandbox_protected` 看有没有残留 `(DENY)` 项。这个副作用恰好印证了"DENY 优先命中且影响面广"——正是形态 B 粒度粗（目录级、影响同 SID 所有主体含 explorer）的体现，和形态 A 的逐请求细粒度形成对比。

## 七、面试三连问

**Q1：你的文件 broker 怎么防路径穿越 / symlink 绕过？**
A：不靠"对字符串路径判白名单再打开"（有 TOCTOU）。我先用请求的 access 打开句柄，再用 `GetFinalPathNameByHandleW` 让内核回吐这个句柄**真正指向**的规范全路径（symlink/junction/短名/大小写都已解析），拿这个事后真身去比白名单——校验对象和使用对象是同一个内核文件对象，检查时机攻击无从下手。创建类请求就退化为校验父目录真身。

**Q2：broker 把句柄传给不可信 target，怎么保证不放大权限？**
A：两层。协议层 target 只能传 `AccessMode` 三种枚举，不能传裸 Win32 权限位，broker 内部翻译成收敛过的 access；DuplicateHandle 时按本次策略允许的**最小权限**复制（不是 `DUPLICATE_SAME_ACCESS`），只读请求就只给 `GENERIC_READ`。即使 target 被攻破，句柄权限也就这么大。

**Q3：IPC 代劳和直接改 ACL(DENY-ACE)，什么时候用哪个？**
A：IPC 代劳是"主动授予"，默认全禁、broker 按细粒度策略逐次发句柄，适合 renderer 这种要频繁精确访问工程文件的场景（Chromium sandbox 就是这套）；DENY-ACE 是"被动剥夺"，一条继承 ACE 覆盖整个子树、target 无需改造照常 CreateFileW，适合快速把某目录对某进程只读化。两者互补，纵深防御里常一起用。
