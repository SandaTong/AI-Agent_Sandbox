## 工作内容
- 用户深入追问"crash 时 JobManager 析构不走,Job handle 还会被关吗"。
  确认了关键纠正点:
  - crash 时 C++ 析构**不走**,`ScopedHandle::operator=` 不调用。
  - 但 `KILL_ON_JOB_CLOSE` 依然生效——靠的是**内核**在进程销毁时清理该进程的 handle table,
    逐个关闭所有内核对象 handle(包括 Job 的)→ "最后一个 handle 被关" → 触发。
  - 共同点:都靠"最后一个 handle 关闭"触发,不依赖用户态析构——这才是它作为沙箱生命线的本质。
  - 隐含前提:只有 broker 持有 Job handle。`bInheritHandles=FALSE` 保证 target 不继承 Job handle,
    否则 broker 死了 handle 不到 0,KILL_ON_JOB_CLOSE 在 crash 场景就不会触发。
    (所以 `bInheritHandles=FALSE` 不仅为 M3 通信白名单,也间接保证 crash 时兜底生效。)
- 已更新 MEMORY.md,纠正之前"return 时析构触发 KILL_ON_JOB_CLOSE"的不准确表述
  (该表述只在正常退出路径成立,crash 路径下析构不走)。

## 记忆
- 关键洞察:`KILL_ON_JOB_CLOSE` 是内核机制,不依赖用户态代码"好好死"——
  这正是它作为沙箱生命线的核心价值。

- Mitigation 核心机制:`STARTUPINFOEX` + `PROC_THREAD_ATTRIBUTE_LIST`,通过
  `UpdateProcThreadAttribute` 装 `PROC_THREAD_ATTRIBUTE_MITIGATION_POLICY`(位图)+

- 8 项策略(strict 0..8)详解已可视化讲解。其中 strict=7 BLOCK_NON_MICROSOFT_BINARIES 是"反注入绝杀"。
  CHILD_PROCESS_RESTRICTED 虽在 BuildMitigation 里,但它是独立属性,不在 Mitigation 位图内。

## 后续(同日)- 整理 MS 文档:App Capability Declarations
- 用户要在 M2 用 AppContainer,问微软文档 https://learn.microsoft.com/en-us/windows/uwp/packaging/app-capability-declarations 怎么理解。
- 抓取并整理全文(146 个能力)。核心机制可视化讲解:
  - 能力声明(Capability)在 Package.appxmanifest 里写,启动时系统读清单把能力转成 LowBox Token 里的"能力 SID"。
  - AppContainer 进程访问资源时,SRM 用能力 SID 比对资源 SD 的 ACE(默认拒绝,声明什么才能用什么)。
  - 四大类:通用 Capability / 设备 DeviceCapability / 受限 rescap:Capability / 自定义 CustomCapability。
    manifest 里顺序强制:Capability → rescap → Custom → Device。
  - 隐私敏感(*标记)建议声明,会在 Windows 设置里出现开关,用户可随时关闭。
- M2 在沙箱三层防护中的位置:M0 管"特权+资源"、M1 管"反exploit+IL"、M2 管"身份隔离+资源白名单"。
  M2 填的缺口:target 不再以原用户身份访问文件,而是 AppContainer 身份 + 能力 SID,ACL 默认拒绝。
- M2 实操要点:沙箱 target 通常只需通用能力(如 internetClient),受限能力(runFullTrust/broadFileSystemAccess)
  本身就违背沙箱原则,不该用。
